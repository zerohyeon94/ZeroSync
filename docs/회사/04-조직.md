# 04. 조직과 직원 (제품 부서)

> 상태: 초안 (2026-10-28). 구성은 Zero 결정, 팀장 역량·성격 설명은 Zero 검토 대기
> 회사 재정의 4단계. 3단계 업무 흐름의 각 단계를 누가 맡는지 정한다. ADR-006(팀장 직접 보고, 채용 방식, 엔진)을 검증하고 바뀌는 점을 적는다.
> 교육·비서 부서의 담당 에이전트는 그 부서의 흐름을 정할 때 함께 정한다.

---

## 1. 조직도

```
Zero (대표, 제품 부서장)
└─ 제품 부서
   ├─ 기획팀   Beta  (INFJ)  팀장. 배포 업무 겸임
   ├─ 디자인팀 Gamma (ISFP)  팀장. 2026-10-28 채용
   ├─ 개발팀   Alpha (INTJ)  팀장
   └─ QA팀     Delta (ISTJ)  팀장. 검증과 테스트 진단. 2026-10-28 채용
교육 부서, 비서 부서: 담당 미정 (Zero와 1대1, 부서 흐름을 정할 때)
```

- 팀장마다 Zero에게 직접 보고한다 (헌장 3.0). 팀원은 아직 없다
- 헌장 3.1의 검증팀·테스트팀은 QA팀 하나로 합친다. 배포팀은 두지 않고 Beta가 겸임한다
- 엔진은 모두 Claude로 시작한다 (ADR-006). 같은 엔진이라도 QA는 만든 쪽과 다른 에이전트가 새 세션에서 읽기 전용으로 본다
- 표시 이름은 `[이름 · 직책]`이다 (SPEC Q16). 예: `[Gamma · 디자인팀장]`, `[Delta · QA팀장]`

---

## 2. 흐름별 담당

3단계 [03-업무-흐름.md](03-업무-흐름.md) 4장의 흐름에 담당을 붙인다.

| 흐름 | 단계 | 담당 |
|------|------|------|
| 대화 | 의견 | 부르면 그 팀장. 아무도 안 부르면 Beta와 Alpha |
| 기능 개발 | 기획 | Beta |
| | 화면 디자인 | Gamma |
| | 기술 설계, 구현, 지적 수정 | Alpha |
| | 테스트 | 봇 |
| | 검증 (리뷰) | Delta |
| | 문서 반영안 | Beta |
| 버그 수정 | 진단 | Delta |
| | 수정 | Alpha |
| | 테스트 | 봇 |
| | 검증 (리뷰) | Delta |
| 출시 | 출시 점검 | 봇 |
| | 출시 준비 (점검 목록, 버전, 릴리스 노트·스토어 설명 초안, 인증서 만료 확인) | Beta (배포 겸임) |
| 정기 테스트 | 테스트 | 봇 |
| | 실패 진단 | Delta |
| 아이디어 관리 | 기록 | 봇 (`/idea`) |

- 기능 개발의 검증을 Delta가 맡으므로 SPEC 3.5의 규칙 R1("리뷰 담당은 같은 작업의 기획·설계·구현 담당과 다르다")을 지킨다. 지금 SPEC 예시(`feature.yaml`)는 기획과 리뷰를 모두 Beta에게 두어 R1과 충돌한다. 6단계에서 예시를 고친다
- 버그 수정에서는 Delta가 진단한 수정을 Delta가 다시 검증한다. R1은 진단 담당을 막지 않는다. 진단은 수정 방향 제안일 뿐이고 수정은 Alpha가 하므로 그대로 둔다

## 3. 새로 채용하는 팀장

ADR-006 2장과 같은 형식으로 역량과 성격을 적는다. 인격 파일(`agents/<이름>.md`)은 이 내용으로 만든다 (SPEC Q12).

### 3.1 Gamma · 디자인팀장 (ISFP)

| 역량 | 내용 |
|------|------|
| 기획 의도를 화면으로 옮기기 | 기획서의 사용자 흐름을 화면 구성, 컴포넌트, 상호작용으로 바꾼다 |
| 디자인 시스템 유지 | 제품마다 디자인 시스템(색, 글꼴, 컴포넌트)을 지키고, 바꿀 때는 이유를 적는다 |
| 화면 상태를 빠짐없이 | 빈 화면, 로딩, 오류, 긴 글, 큰 글씨(접근성) 상태를 모두 그린다 |
| 플랫폼 규칙 | iOS Human Interface Guidelines를 따른다 |
| 개발팀에 넘기기 | 개발팀이 그대로 구현할 수 있는 명세(md)를 쓴다 (03-업무-흐름 6장) |

성격: ISFP. 사용자가 화면에서 느끼는 감정과 세부 감각에 민감하다. 혼자 깊이 다듬는 데 강하다.

위험과 보완: 보기 좋은 쪽으로 기울어 기획 범위를 넘을 수 있다 → 기획서에 없는 화면을 추가하면 "기획 밖 제안"으로 따로 표시한다. 일정보다 완성도에 끌릴 수 있다 → 디자인 단계에도 호출 상한(SPEC Q18)을 둔다.

### 3.2 Delta · QA팀장 (ISTJ)

| 역량 | 내용 |
|------|------|
| 기준 대조 | 기획서, 디자인 명세, 설계 문서와 구현을 항목별로 맞춰 본다 |
| 코드 품질 | 동시성, 메모리, 오류 처리, 경계값을 본다 (ADR-006에서 약점으로 적은 부분) |
| 테스트 실패 진단 | 재현 방법, 원인 분류(코드 결함, 테스트 결함, 환경 문제), 수정 방향을 보고한다 |
| 판정 형식 | 리뷰 판정 형식(운영 규약 2.3)을 지키고 지적마다 근거 위치를 단다 |
| 읽기 전용 | 코드를 고치지 않는다. 지적과 진단만 한다 |

성격: ISTJ. 정해진 기준을 빠짐없이 차례로 확인한다. 같은 검사를 반복해도 질이 떨어지지 않는다.

위험과 보완: 기준 문서에 없는 문제(사용 흐름의 어색함, 설계 자체의 문제)를 놓칠 수 있다 → 판정에 "기준 밖 우려"를 최소 1개 쓰게 한다 (의견의 위험 필수 규칙과 같은 방식). 지적이 사소한 것까지 늘어날 수 있다 → 지적 등급(필수, 권장, 참고)을 지킨다.

## 4. 겸임과 다음 채용

| 겸임 | 지금 | 채용을 제안할 신호 |
|------|------|------------------|
| 배포 | Beta | 출시가 몇 번 쌓여 출시 준비가 기획 일을 밀어낼 때, 스토어 제출 자동화를 시작할 때 |

- 채용 제안은 팀장이 보고에 근거를 붙여 먼저 한다 (ADR-006 채용 방식, 운영 규약 1.12). 다음 이름은 Epsilon이다
- 교육·비서 담당은 채용이 아니라 부서를 시작할 때 Zero가 정한다

---

## 5. ADR-006에서 바뀌는 점

6단계에서 ADR-007로 남기고 ADR-006, 운영 규약, SPEC에 반영한다.

| ADR-006 | 바뀐 것 |
|---------|--------|
| 팀장이 Zero에게 직접 보고하는 한 층 | 부서 → 팀 두 층. Zero가 제품 부서장을 겸임하므로 제품 팀장의 보고 방식은 같다. 교육·비서는 1대1 |
| 기획팀(Beta), 개발팀(Alpha) | 제품 부서 소속. 디자인팀(Gamma), QA팀(Delta)을 처음부터 둔다 |
| QA팀을 채용하기 전까지 Beta가 리뷰 | 리뷰는 처음부터 Delta. Beta는 리뷰하지 않는다 |
| 채용 이름 Gamma, Delta, Epsilon … (분야 미정) | Gamma = 디자인, Delta = QA. 다음은 Epsilon |
| 배포는 Zero 승인 | 같다. 배포 준비는 Beta 겸임, 스토어 제출은 Zero가 직접 |
