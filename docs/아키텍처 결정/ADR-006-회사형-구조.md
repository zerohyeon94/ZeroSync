# ADR-006 — ZeroSync를 팀 단위 회사 구조로 재설계

> 날짜: 2026-10-26 | 상태: 초안 (Zero 검토 전) | 이전 결정: [ADR-005](ADR-005-Discord-오케스트레이터-전환.md) | 설계: [SPEC](../SPEC.md) 11.1 Q12~Q18

---

## 결정

ZeroSync를 "에이전트 두 명이 한 흐름을 처리하는 봇"에서 **Zero가 대표로 있고, 팀장이 팀을 맡아 여러 프로젝트를 운영하는 회사 구조**로 재설계한다.

회사가 하는 일은 두 가지다.

- **운영 중인 프로젝트:** 개선, 유지보수, 의견 교환
- **새로 시작하는 프로젝트:** 아이디어 → 디자인 → 기획 → 개발

ADR-005의 원칙(봇은 결정론적 프로그램, 판단은 Zero만, 외부 쓰기는 봇 하나, 워크플로 로직은 Discord와 분리)은 그대로 유지한다.

### 1. 조직

```
Zero (대표, 최종 판단)
 ├─ 기획팀 — 팀장 Beta
 └─ 개발팀 — 팀장 Alpha
     (디자인팀, QA팀, 운영팀 … 은 필요할 때 채용)
```

- 임원 층은 두지 않는다. 각 팀장이 Zero에게 직접 보고한다. 팀이 늘어 종합 보고가 필요해지면 그때 임원을 만든다
- 조직도는 설정 파일로 정하고 **Zero만 바꾼다**. 팀장을 포함한 어떤 에이전트도 팀이나 역할을 만들 수 없다
- 인격(MBTI)은 말투와 관점에만 적용한다. 출력 형식(JSON 스키마)은 인격과 무관하게 지킨다

### 2. 팀장

#### 기획팀 팀장 — Beta (INFJ)

| 역량 | 내용 |
|---|---|
| 문제 정의 | 아이디어에서 "누구의 어떤 문제인가"를 먼저 꺼낸다. 해결책부터 말하지 않는다 |
| 사용자 관점 | 실제 사용 흐름(진입, 실패, 되돌리기)을 기준으로 기능을 판단한다 |
| 범위 결정 | 이번에 할 것과 하지 않을 것을 나눈다. 우선순위의 근거를 적는다 |
| 기획서 작성 | 개발팀이 질문 없이 설계를 시작할 수 있는 수준으로 목표, 범위, 완료 기준, 예외 상황을 쓴다 |
| 일관성 유지 | 프로젝트 안의 기존 기능, 용어, 화면 흐름과 어긋나지 않는지 확인한다 (볼트 `기능/` 문서 기준) |
| 운영 개선 | 운영 중인 프로젝트에서 사용자 불편과 반복 문의를 개선 과제로 바꾼다 |

성격: **INFJ**

- 직관(N)으로 아이디어의 방향과 사용자에게 주는 의미를 본다. 새 프로젝트 기획에 필요하다
- 감정(F)으로 사용자 경험과 불편을 우선한다. 기존 Beta(ISFJ)의 사용자 경험 관점을 잇는다
- 판단(J)으로 아이디어를 범위와 완료 기준이 있는 기획서로 닫는다
- 내향(I)이라 아이디어를 넓히기보다 다듬는 쪽이다. 아이디어를 넓히는 대표 Zero(ENFJ)와 겹치지 않고 보완한다
- 기존 ISFJ에서 바꾸는 이유: ISFJ는 유지보수와 일관성에는 맞지만, 새 프로젝트의 아이디어·방향 설정에는 직관(N)이 필요하다 [제안]

#### 개발팀 팀장 — Alpha (INTJ)

| 역량 | 내용 |
|---|---|
| 기술 설계 | 기획서를 구조(모듈, 데이터, 상태, 의존성)로 옮기고 변경 범위를 정한다 |
| 구현 | 설계대로 코드를 쓰고, 작은 단위로 커밋한다 |
| 위험 판단 | 실행 위험(데이터 손실, 마이그레이션, 성능, 보안)과 되돌리기 방법을 먼저 적는다 |
| 테스트 기준 | 무엇을 어떻게 확인하면 완료인지 테스트 계획으로 정한다 |
| 기존 코드 존중 | 작업을 만들기 전에 실제 코드를 읽는다. 이미 있는 것을 다시 만들지 않는다 |
| 운영 대응 | 빌드·배포 실패, 크래시, 인증서 만료 같은 운영 문제의 원인을 분류하고 수정안을 낸다 |

성격: **INTJ** (기존 Alpha 유지)

- 직관(N)과 사고(T)로 구조와 장기 위험을 본다
- 판단(J)으로 계획을 세우고 그대로 끝까지 실행한다
- 기획팀장(INFJ)과 N·J를 공유해 대화가 통하고, T·F 차이로 "만들 수 있는가"와 "써야 하는가"가 서로 견제된다

### 3. 채용

팀과 팀원은 Zero가 채용으로만 늘린다.

- **새 팀:** 디자인, QA, 운영 등 필요한 시점에 Zero가 채용한다. 이름은 그리스 문자 순서(Gamma, Delta, Epsilon …)로 붙이고, 성격(MBTI)과 역량은 채용할 때 Zero가 정한다
- **팀원:** 지금은 팀원이 없다. 팀장이 다음 경우에 해당하면 팀원 채용을 **제안**할 수 있고, 채용 여부는 Zero가 정한다
  - 팀장 혼자서는 의견의 폭이 부족해 다른 관점이 더 필요할 때
  - 특정 업무를 실제로 맡아 처리할 담당 에이전트가 필요할 때 (예: 개발팀의 구현 담당, 기획팀의 리서치 담당)
- 채용 제안에는 이유, 맡길 업무, 원하는 성격·역량을 적는다. 팀장은 제안만 하고, 설정을 바꾸는 것은 Zero다
- 채용 기록(이름, 팀, 직책, 엔진, 성격, 역량, 채용일, 이유)은 설정 파일과 개발 일지에 남긴다

### 4. 엔진

- 처음에는 모든 에이전트를 **Claude**로 운영한다
- 에이전트마다 엔진을 설정으로 지정한다. Codex는 설정만 바꿔 언제든 붙일 수 있게 둔다 (기존 `CodexCliRunner` 유지)
- 에이전트 이름은 엔진과 분리한다. Alpha는 더 이상 "Codex"를 뜻하지 않는다

### 5. 검증

엔진이 하나가 되면 다른 모델이 검증하던 장점이 사라진다. 대신 아래 규칙을 둔다.

- 만든 에이전트와 검증하는 에이전트를 다르게 둔다. 지금은 Alpha가 구현하면 Beta가 기획서·설계 기준으로 리뷰한다
- 리뷰는 구현 대화를 이어받지 않고 새 세션에서 읽기 전용으로 한다
- 테스트는 지금처럼 에이전트가 아니라 봇이 실행하고 결과를 직접 확인한다
- QA팀을 채용하면 리뷰를 QA로 넘긴다. Codex를 다시 붙이면 가장 먼저 리뷰에 배치한다

### 6. 자율성

- 승인 게이트의 위치를 파이프라인마다 선언한다
- 신규 기획 확정, merge, 배포는 항상 Zero가 승인한다
- 진단, 제안처럼 외부에 쓰지 않는 일은 승인 없이 끝까지 진행하고 결과만 보고할 수 있다

### 7. 입력과 화면

- 논의와 승인은 Discord에서 한다
- 여러 프로젝트·파이프라인의 현황과 지표(도달, 채택, 자동 제외, 시스템 실패, 병목)는 로컬 대시보드에서 본다
- 입력 경로는 Discord 외에 Slack 봇, 로컬 Jenkins, 테스트 베드 SSH를 받을 수 있게 입력 계층을 둔다

### 8. 공개 범위

- 엔진(봇 코드)은 공개 저장소에 둔다
- 회사 업무용 어댑터(Slack, Jenkins, SSH)와 파이프라인 정의, 회사 프로젝트 설정은 비공개 저장소나 커밋하지 않는 설정 폴더에 둔다

## 맥락

- ADR-005 이후 한 흐름(의견 → 결정 → 설계 → 구현 → 리뷰 → merge)은 Phase 2까지 구현했다. GagaeSsi 실제 사이클은 아직 끝까지 확인하지 못했다
- Zero는 여러 프로젝트를 동시에 관리하려 한다. 운영 중인 프로젝트의 유지보수와 새 프로젝트의 기획·개발은 필요한 역할이 다르다
- 회사 업무에는 이미 Slack 통합 접수, 로컬 Jenkins(빌드·상태 확인·iOS 인증서·새벽 시나리오 테스트), 테스트 베드 SSH 트리거가 있다. 이를 한 화면에서 같은 틀로 보려는 목업을 Zero가 그렸다 (파이프라인별 단계, 승인 게이트, 지표, 병목)
- 지금 구조는 Beta·Alpha 두 에이전트와 고정된 상태 머신 하나라, 역할과 파이프라인을 늘릴 방법이 없다

2026-10-26에 Claude로 회사를 꾸리는 공개 사례를 조사했다. 성과 수치는 대부분 자기 보고라 검증하지 않았다.

| 유형 | 사례 | 구조 | 사람의 역할 |
|---|---|---|---|
| 조직도형 오케스트레이터 | Paperclip | 회사·목표·조직도·티켓, 정해진 시각에 깨우기, 예산 상한, 승인 단계, 다중 회사 | 목표·채용·예산 승인, 일시정지 |
| 파일 기반 자율 회사 | DEV 글 (Claude Code만으로 만든 회사) | CLAUDE.md가 정관, CEO도 Claude, 부서는 폴더, 기록은 덧붙이기만 | 사업 개시·중단, 공개 출시, 정관 변경 승인 |
| 역할별 기술 파이프라인 | gstack | 역할 = 슬래시 명령, 아이디어 검증 → CEO 리뷰 → 엔지니어링 리뷰 → 구현 → 리뷰 → QA → 출시 → 회고 | 단계마다 직접 실행 |

| Claude Code 내장 기능 | Agent Teams (실험) | 리드 1명과 팀원, 공유 작업 목록, 메일함 | 대화형 세션에서 지휘 |

사례에서 얻은 교훈:

- CEO 에이전트에게 넓은 권한을 주자 역할 20개를 만들고 메모·회의만 돌며 일이 멈췄다 (HN). → 조직도는 Zero만 바꾼다
- 파일 변경으로 다음 에이전트를 자동으로 띄우자 상태 보고만 늘어 되돌렸다 (HN). → 승인 게이트를 파이프라인마다 선언한다
- 작업이 크면 실수도 크다. 코드를 읽지 않고 이미 있는 기능을 작업으로 만들었다 (HN). → 개발팀장 역량에 "기존 코드 존중"을 넣는다
- 인프라를 더할 때마다 취약해졌다 (DEV). → 기존 SQLite·Discord 구조 위에서 확장한다
- Agent Teams는 `-p` 비대화형 모드에서 동작하지 않는다. → 봇이 CLI를 호출하는 지금 구조에 바로 쓸 수 없다. 팀 구조는 봇이 결정론적으로 조율한다

| 항목 | 선택지 | 결정 |

| 에이전트 구성 | 두 인격에 역할 모자 / 직군별 팀장·팀원 | 직군별 팀장·팀원. 처음에는 팀장 2명, 팀원 없음 |

| 조직 변경 권한 | 에이전트가 만든다 / Zero만 바꾼다 | Zero만. 팀장은 채용을 제안만 한다 |

| 공개 범위 | 전부 공개 / 엔진 공개·회사 설정 비공개 / 저장소 비공개 | 엔진 공개, 회사 설정 비공개 |
| 주 화면 | Discord / 대시보드 / Slack | Discord에서 논의·승인, 대시보드에서 현황 |

## 근거

- 조직도를 설정으로 고정하면 사례에서 반복된 "에이전트가 조직을 키우다 일이 멈추는" 실패를 구조적으로 막는다. 봇이 결정론적이라는 ADR-005의 원칙과도 맞다
- 팀장 2명으로 시작하면 호출 수와 대기 시간이 지금과 비슷하다. 필요할 때만 채용하므로 비용이 일에 비례해 늘어난다
- 엔진을 이름에서 떼어 두면, 사용량·품질에 따라 엔진을 바꿔도 조직과 기록이 바뀌지 않는다
- 기존 Phase 1·2 코드(스키마 검증, 상태 머신, 테스트 실행, GitHub 계층, 대시보드)는 팀 구조에서도 그대로 쓴다

## 트레이드오프

- **검증 약화:** 다른 모델의 교차 검증이 사라진다. 같은 모델은 같은 맹점을 가질 수 있다. 5절의 규칙으로 줄이지만 완전히 대신하지는 못한다. 첫 채용으로 QA팀을 우선 검토한다
- **기획팀장의 코드 리뷰:** QA팀을 채용하기 전까지 Beta가 기획서·설계 기준으로 리뷰하므로, 코드 품질 자체(동시성, 성능 등)의 리뷰는 약하다
- **호출 증가:** 팀원과 팀이 늘면 안건 하나당 CLI 호출과 대기 시간이 늘어난다. 예산 상한을 파이프라인·에이전트 단위로 둬야 한다
- **문서·코드 변경 범위:** 운영 규약, SPEC, 프롬프트, 상태 머신의 "Beta가 구현, Alpha(Codex)가 리뷰" 가정을 바꿔야 한다
- **저장소 개발 규칙과의 구분:** `CLAUDE.md`·`AGENTS.md`의 "Claude = Beta, Codex = Alpha"는 이 저장소를 개발하는 코딩 에이전트의 규칙이다. 봇 안의 에이전트 구성과 이름이 겹치므로 두 문서에서 구분해 적어야 한다

## 이후 할 일

- Zero 검토 후 이 ADR을 확정한다. Beta의 성격 변경(ISFJ → INFJ)도 이때 확정한다
