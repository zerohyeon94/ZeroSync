# 05. 운영 방식 (제품 부서)

> 상태: 확정 (2026-10-28). 제안으로 적었던 항목도 Zero가 제안대로 확정
> 회사 재정의 5단계. 제품 부서가 매일 어떻게 돌아가는지 정한다: 보고, 승인, 순서와 동시 진행, 예산, 대시보드, 기록, 정보 보호.

---

## 1. 보고 (2026-10-28 Zero 결정)

| 보고 | 언제 | 어디 | 내용 | 만드는 주체 |
|------|------|------|------|-----------|
| 단계 보고 | 단계가 끝날 때마다 | 해당 포럼 포스트 | 그 단계의 결과 요약과 링크 (기획서, 디자인, PR, 테스트 결과 등) | 담당 팀장 (봇이 게시) |
| 아침 보고 | 매일 08:00 [제안] | `#대표실` | Zero가 승인할 것, 진행 중인 일, 어제 끝난 일, 어제 예산 사용 | 봇 (DB에서 만든다. 에이전트 호출 없음) |
| 주간 보고 | 매주 월요일 08:00 [제안] | `#대표실` | 제품별 진행, 성공 기준 지표(헌장 5장), 예산 사용 추이, 팀장의 채용 제안 | 봇 (숫자) + 채용 제안은 팀장 보고에서 옮김 |

- `#대표실`은 Zero에게 올라오는 보고와 승인 대기만 모은다. 봇 시작·종료·오류는 지금처럼 `#zerosync-ops`에 둔다
- 아침 보고는 Zero가 해야 할 일이 있을 때만 멘션한다. 없으면 알림 없이 게시한다 (운영 규약 2.5의 멘션 규칙)
- 채용 제안은 팀장이 단계 보고의 `hiring_proposal`로 내고(SPEC Q19), 주간 보고에 모아 보여 준다. `/hire`로 답하는 방식은 같다

## 2. 승인

3단계에서 정한 승인 지점을 한곳에 모은다.

| 흐름 | 승인 지점 | 방법 |
|------|----------|------|
| 모든 흐름 | 시작 | 채팅에서 `/task`, `/release` (명령 자체가 결정) |
| 기능 개발 | 기획, 화면 디자인, merge, 문서 반영 | `/approve`·`/revise`, merge는 GitHub에서 |
| 버그 수정 | 수정 방향(진단 뒤), merge | 같음 |
| 출시 | 출시 (준비물 확인 뒤) | `/approve`. 스토어 제출은 Zero가 직접 |
| 외부로 나가는 글 | 릴리스 노트, 스토어 설명 등 | 출시 승인에 포함 |

- 승인을 기다리는 일은 저절로 넘어가지 않는다. 24시간이 지나면 한 번 다시 멘션하고(SPEC 3.3), 아침 보고의 "승인할 것"에 계속 남는다

---

## 3. 순서와 동시 진행 (2026-10-28 Zero 결정)

- 에이전트는 **한 번에 하나만** 실행한다. 테스트·빌드도 한 번에 하나다 (지금의 전역 테스트 락)
- 기다리는 일은 다음 순서로 꺼낸다
  1. Zero가 방금 답한 일 (승인, 질문에 대한 답): 사람을 기다리게 하지 않는다
  2. 제품 우선순위: 가게씨 → 제이데이 → 오롯 (02-프로젝트 3.3)
  3. 같은 제품 안에서: 버그 수정 → 출시 → 기능 개발
  4. 먼저 들어온 순서
- 채팅의 답(대화)은 위 순서와 같은 대기열에 들어간다. 정식 흐름이 길게 돌고 있으면 채팅 답이 늦어질 수 있다 [제안: 채팅은 1번과 같은 순위로 올린다]
- 대기 시간이 길어지면 대시보드의 병목에 보인다. 그때 동시 실행 수를 늘릴지 다시 정한다
- 부서 우선순위(교육 → 비서 → 제품)는 교육·비서 부서를 시작할 때 이 대기열에 더한다

## 4. 예산 (2026-10-28 Zero 결정: 시작값을 두고 조정)

시작값이다. 2주 쓴 뒤 주간 보고의 사용량을 보고 고친다. 넘으면 그 일은 NEEDS_HUMAN이 되고 `#zerosync-ops`에 알린다 (SPEC Q18).

| 대상 | 호출 수 | 실행 시간 |
|------|--------|----------|
| 팀장마다 하루 (Beta, Gamma, Alpha, Delta) | 30회 (채팅 답 포함) | - |
| 기능 개발 1회 | 25회 | 4시간 |
| 버그 수정 1회 | 12회 | 2시간 |
| 출시 1회 | 8회 | 1시간 |
| 정기 테스트 실패 진단 1회 | 3회 | 30분 |

- 기능 개발 25회의 근거: 기획 2, 화면 디자인 2, 기술 설계 1, 구현 1, 테스트 실패 수정 최대 2, 검증 최대 3, 검증 지적 수정 최대 3, 문서 반영 1 = 15. 재요청(형식 오류)과 Zero의 수정 요청(`/revise`) 여유를 더했다
- 구독 사용량 한도에 걸리면(CLI가 한도 오류를 낼 때) 대기열 전체를 멈추고 `#zerosync-ops`에 알린다. 한도가 풀리는 시각이 오면 다시 시작한다 [제안] [검증 필요: CLI가 한도 오류를 어떻게 알리는지]

## 5. 대시보드 [제안]

지금의 로컬 대시보드(`python -m bot.dashboard`, SQLite 읽기 전용)를 넓힌다. Zero의 목업(파이프라인 카드, 단계, 승인 게이트, 지표, 병목)을 기준으로 한다.

| 화면 | 내용 |
|------|------|
| 홈 | 승인 대기 목록(가장 위), 지금 실행 중인 일, 대기열, 오늘 예산 사용 |
| 제품별 작업판 | 제품마다 흐름 카드. 카드에 지금 단계, 승인 대기 여부, 걸린 시간 |
| 지표 | 헌장 5장의 제품 기준: 출시·업데이트 수, 자동 처리 비율, 품질(merge 후 되돌림, 테스트 통과율) |
| 병목 | 단계별 평균 대기 시간. Zero 승인 대기와 에이전트 실행 대기를 나눠 보여 준다 |
| 아이디어 | `/idea`로 모은 목록, 제품별 |
| 예산 | 팀장별·흐름별 사용량 추이 |

목업의 지표 이름을 제품 부서에 맞춰 이렇게 정의한다.

| 목업 지표 | 제품 부서에서의 뜻 |
|----------|-----------------|
| 도달 | 시작된 흐름 수 (`/task`, `/release`, 정기 테스트 실패 보고) |
| 채택 | merge되었거나 출시된 흐름 수 |
| 자동 제외 | Zero가 닫았거나 반려한 흐름 수 |
| 시스템 실패 | 에이전트 실행 오류, 형식 오류, 예산 초과로 NEEDS_HUMAN이 된 수 |

## 6. 기록 위치 [제안]

운영 규약 3.2의 "정보마다 원본은 한 곳" 원칙을 새 정보에 적용한다.

| 정보 | 원본 | 다른 곳 |
|------|------|--------|
| 대화(채팅) | Discord 채팅 채널 | `/task` 때 요약을 포스트로 |
| 화면 디자인 명세 | 앱 저장소 `docs/디자인/<Issue번호>-<slug>.md` | Claude 디자인 링크는 명세 안에. Discord·Issue에는 요약과 링크 |
| 제품 디자인 시스템 | Claude 디자인 시스템(제품마다 1개) | 링크를 회사 설정(`zerosync-company`)에 |
| 진단 보고 | 봇 DB (에이전트 출력 JSON) | 포럼 포스트와 Issue에 요약 |
| 아이디어 목록 | 봇 DB | 대시보드. 볼트(`Projects/아이디어 목록.md`)에는 옮기지 않는다. 볼트 쓰기 허용 경로(운영 규약 3.4)를 늘리지 않기 위해서다 |
| 아침·주간 보고 | 봇 DB에서 매번 만든다 | `#대표실` |

## 7. 정보 보호 [제안]

- 이 저장소는 공개다. 팀장 인격 파일, 파이프라인 YAML, 제품 디자인 시스템 링크 등 회사 설정은 비공개 저장소(`zerosync-company`)에 둔다 (SPEC Q17)
- Claude 디자인 결과물은 claude.ai 비공개 페이지다. 공유 범위를 넓히지 않는다
- 개인 메일은 비서 부서의 메일 정리를 시작할 때 정한다 (헌장 7장). 지금은 어떤 에이전트도 메일에 접근하지 않는다
