# 03. 업무 흐름 (제품 부서)

> 상태: 초안 (2026-10-27)
> 회사 재정의 3단계. 제품 부서가 하는 일의 종류마다 흐름, 채널, 승인 지점, 맡는 팀을 정한다. 교육·비서 부서의 흐름은 제품 부서를 완성한 뒤 정한다 (2026-10-27 Zero 결정).
> 팀 이름은 헌장 3.1의 큰 틀(기획, 개발, 검증, 테스트, 배포)을 쓴다. 팀마다 어느 에이전트를 둘지는 4단계에서 정한다.
> `[미결]`은 Zero가 아직 정하지 않은 항목이다.

---

## 1. 일의 종류

2단계의 제품 목록과 목표에서 나온 일이다.

| 종류 | 언제 생기나 | 예 | 해당 제품 |
|------|-----------|----|----------|
| 대화 | Zero가 아이디어를 꺼내거나 팀장 의견을 듣고 싶을 때 | "예산 초과 알림을 바꾸면 어떨까?" | 모두 |
| 기능 개발 | 새 기능이나 개선을 하기로 했을 때 | 위젯 추가, 화면 개편 | 모두 |
| 버그 수정 | 문제를 발견했을 때 | 크래시, 테스트 실패 | 모두. 가게씨 안정화의 중심 |
| 출시 | 첫 출시나 업데이트를 내보낼 때 | 가게씨 첫 출시, 제이데이 업데이트 | 모두 |
| 정기 테스트 | 정해진 시각마다 | 매일 밤 전체 테스트 | 모두 |
| 아이디어 관리 | 바로 하지 않을 생각을 모아 둘 때 | 오롯의 개선 아이디어 | 주로 오롯 |

---

## 2. 팀이 맡는 것

| 팀 | 맡는 것 | 하지 않는 것 |
|----|--------|------------|
| 기획 | 대화에서 의견, 기획서(무엇을 왜, 화면 흐름 포함), 문서 반영안 | 코드 변경 |
| 개발 | 대화에서 의견, 설계, 구현, 리뷰 지적 수정 | 자기 코드의 검증 |
| 검증 | 만든 것이 기획서와 맞는지, 코드가 올바른지 확인. 새 세션에서 읽기 전용 (ADR-006 검증 규칙) | 코드 수정 |
| 테스트 | 무엇을 테스트할지 정리, 테스트 실패 원인 진단, 정기 테스트 결과 보고. 테스트 명령 실행은 봇이 한다 | 코드 수정 |
| 배포 | 출시 점검 목록, 버전 번호, 릴리스 노트·스토어 설명 초안, 인증서·프로비저닝 만료 확인 | 스토어 제출 실행 (4.4) |

검증과 테스트를 이렇게 나눈다.
- **테스트**: 정해진 테스트를 실행하고(봇), 실패하면 원인을 찾는다(테스트팀). "돌아가는가"를 본다
- **검증**: 사람이 리뷰하듯 기획서와 코드를 읽고 판정한다. "맞게 만들었는가"를 본다

`[미결]` 디자인(화면 디자인)을 누가 맡을지 (5장 질문 4).

## 3. 채널과 흐름의 관계

| 채널 | 들어오는 일 | 흐름 |
|------|-----------|------|
| `#<제품>-chat` | 대화, 아이디어 기록 | 상태 머신 없이 답만 한다 |
| `#<제품>` 포럼 | 기능 개발, 버그 수정, 출시, 정기 테스트 보고 | 포스트 하나가 흐름 하나. 단계마다 팀이 보고한다 |

채팅에서 포럼으로 넘기는 명령 (이름은 제안)

| 명령 | 하는 일 |
|------|--------|
| `/task feature <제목>` | 기능 개발 포스트를 연다. 채팅의 의견 요약을 첫머리에 옮긴다 |
| `/task bug <제목>` | 버그 수정 포스트를 연다 |
| `/release <버전>` | 출시 포스트를 연다 |
| `/idea <내용>` | 아이디어 목록에 적는다. 포스트를 열지 않는다 |

`/task`를 쓰는 것 자체가 Zero의 "하기로 한다" 결정이다. 지금의 `/decide`는 이 명령으로 대신한다.

## 4. 흐름

표기: `[Zero]`는 Zero 승인 지점, `(봇)`은 봇이 직접 하는 단계다. 괄호 안 영문은 SPEC 3.5의 단계 종류(kind)다.

### 4.1 대화

```
Zero가 #<제품>-chat에 글 → 부른 팀장이 답 → (계속 대화) → 필요하면 /task 또는 /idea
```

- `@beta`, `@alpha`처럼 부르면 그 팀장이 답한다
- `[미결]` 아무도 부르지 않았을 때 누가 답할지 (5장 질문 3)
- 팀장의 답은 지금의 의견 형식(입장, 결론, 근거, 위험, 제안)을 쓴다. 위험을 최소 1개 쓰는 규칙(운영 규약 2.2)도 그대로다
- 대화 기록은 Discord에만 남는다. `/task`를 할 때 봇이 요약을 포스트로 옮긴다 (운영 규약 3.1)

### 4.2 기능 개발

```
/task feature
  → 기획 (plan, 기획팀) → [Zero 기획 승인] (gate)
  → 설계 (design, 개발팀) → 구현 (implement, 개발팀)
  → 테스트 (test, 봇) → 실패하면 개발팀 수정, 최대 2회
  → 검증 (review, 검증팀, 최대 3라운드) → 지적이 있으면 개발팀 수정
  → [Zero merge] (merge_gate)
  → 문서 반영 (doc_sync, 기획팀) → [Zero 문서 승인]
```

- SPEC 3.5의 `feature.yaml`과 같고, 의견 단계(`opinions`)만 채팅으로 옮겨 빠졌다
- 지금 구현(Phase 2 브랜치)의 설계~merge 단계를 그대로 다시 쓸 수 있다

### 4.3 버그 수정

```
/task bug
  → 진단 (diagnose, 테스트팀): 재현 방법, 원인, 수정 방향 보고
  → [Zero 수정 방향 승인] (gate)
  → 수정 (implement, 개발팀) → 테스트 (test, 봇)
  → 검증 (review, 검증팀)
  → [Zero merge] (merge_gate)
```

- 기획과 설계 단계가 없다. 진단 보고가 그 역할을 한다
- 문서 반영은 기본으로 건너뛴다. 동작이 바뀌는 수정이면 Zero가 `/doc`으로 요청한다 [제안]
- `[미결]` 진단 뒤 승인을 둘지 (5장 질문 1)

### 4.4 출시

```
/release <버전>
  → 출시 점검 (test, 봇): 전체 테스트, 빌드
  → 출시 준비 (배포팀): 점검 목록, 버전 번호, 릴리스 노트·스토어 설명 초안, 인증서 만료 확인
  → [Zero 출시 승인] (gate)
  → 스토어 제출
```

- 릴리스 노트·스토어 설명은 외부로 나가는 글이므로 초안 → Zero 승인 규칙(헌장 4장)을 따른다
- `[미결]` 스토어 제출을 누가 하는지 (5장 질문 2)

### 4.5 정기 테스트

```
봇 일정 (예: 매일 03:00) → 테스트 (test, 봇)
  → 통과: 대시보드에만 기록, Discord에는 알리지 않음
  → 실패: 진단 (diagnose, 테스트팀) → 포럼에 보고 포스트 [확인필요]
        → Zero가 /task bug로 이어가거나 닫음
```

- 실패해도 수정을 저절로 시작하지 않는다. 수정은 Zero가 `/task bug`로 시작한다 (사례에서 본 "자동 연쇄로 보고만 늘어나는" 실패를 피한다)
- 같은 실패가 이어지면 보고 포스트를 새로 열지 않고 기존 포스트에 덧붙인다 [제안]
- 주기와 시각은 제품마다 파이프라인 YAML의 `schedule`에 적는다 (SPEC Q15)

### 4.6 아이디어 관리

```
/idea <내용> (채팅) → 아이디어 목록에 추가
아이디어 목록에서 고른 것 → 채팅에서 대화 → /task feature
```

- 아이디어 목록은 봇 DB에 두고 대시보드에서 본다 [제안]
- 볼트에 이미 `Projects/아이디어 목록.md`와 제품별 `아이디어` 폴더가 있다. 볼트에도 옮겨 적을지는 5단계(운영 방식)에서 정한다

## 5. 정할 것

| # | 질문 | 제안 |
|---|------|------|
| 1 | 버그 수정에서 진단 뒤 Zero 승인을 둘지 | 둔다. 엉뚱한 방향으로 고치는 것을 막는다. SPEC 3.5 규칙 R2(구현 앞에 gate 1개 이상)도 이것으로 지킨다 |
| 2 | 스토어 제출을 누가 하는지 | 처음에는 Zero가 직접 한다. 봇은 준비물까지만. 제출 자동화는 출시를 몇 번 해 본 뒤 정한다 |
| 3 | 채팅에서 아무도 부르지 않았을 때 | 아무도 답하지 않는다(Zero의 메모로 둔다). 호출 수를 아끼고, 답을 원할 때만 부른다 |
| 4 | 디자인 담당 | 지금은 기획팀이 화면 흐름까지 맡는다. 시각 디자인이 필요해지면 기획팀장이 디자인팀 채용을 제안한다 (ADR-006 채용 방식) |
| 5 | 먼저 만들 흐름의 순서 | 대화 → 기능 개발 → 버그 수정 → 출시 → 정기 테스트 → 아이디어 관리. 기능 개발은 Phase 2 구현을 다시 쓰고, 버그 수정은 그 단계들을 재사용하므로 앞에 둔다 |
