# ADR-008: 팀장·팀원 구조와 팀장 확인

- 상태: 확정 (2026-10-28 Zero 결정)
- 관련: [ADR-006](ADR-006-회사형-구조.md), [ADR-007](ADR-007-회사-재정의.md), [운영 규약 1.2, 1.5-1](../운영-규약.md), [SPEC 3.5](../SPEC.md)

## 결정

1. 제품 부서의 개발팀과 QA팀에 팀원을 한 명씩 둔다. 기획팀과 디자인팀은 지금처럼 팀장만 둔다
   - Epsilon (ISTP) · 개발팀원: 구현과 수정(테스트 실패, 리뷰 지적, 팀장 확인 지적)
   - Zeta (INTP) · QA팀원: 버그 진단과 정기 테스트 실패 진단
2. 팀장은 무엇을·어떤 기준으로 할지 정하고(기획, 설계, 확인 기준, 최종 검증), 팀원은 그대로 실행한다
3. 팀원의 결과는 같은 팀 팀장이 확인한다(팀장 확인). 지적이 있으면 팀원이 고치고 다시 확인을 받는다
   - 개발: Epsilon의 구현·수정 → Alpha 확인
   - QA: Zeta의 진단 → Delta 확인
   - 정해진 횟수(기본 2회) 안에 통과하지 못하면 단계 실패로 보고 Zero에게 넘긴다(`NEEDS_HUMAN`)
4. 이름은 기존 규칙(그리스 문자 순서)을 따른다. 다음 이름은 Eta다
5. 운영·배포팀은 나중에 만든다. 지금은 Beta가 출시 준비를 겸임한다

## 맥락

ADR-007까지는 팀마다 팀장 한 명이 판단과 실행을 모두 했다. Alpha는 설계를 opus로, 구현을 sonnet으로 실행해 판단과 실행을 모델 단위로만 나눴다. Zero는 실제 회사처럼 팀장이 방향을 정하고 팀원이 실행하는 구조를 원했다. 팀원 결과를 팀장이 한 번 더 보면 호출 수는 늘지만, 테스트와 QA 검증에 가기 전에 설계와 다른 구현을 걸러 낼 수 있다.

## 선택지

1. 팀마다 팀원을 두고, 팀원 결과를 팀장 확인 없이 다음 단계(테스트, QA 검증)로 넘긴다
2. 팀장 확인을 별도 단계 종류(`lead_check`)로 파이프라인에 넣는다
3. 팀장 확인을 팀원 단계의 속성(`check`)으로 선언하고, 그 단계 안에서 확인과 재작업을 한다 (채택)

QA팀원의 일로는 진단 담당(채택), 진단과 테스트 작성, 1차 검증(리뷰 초안)을 검토했다.

## 근거

- 상태 머신은 "상태 하나가 단계 하나를 가리킨다"는 규칙으로 단계 위치를 찾는다. 별도 단계 종류로 넣으면 버그 수정 흐름에 같은 종류가 두 번(진단 확인, 구현 확인) 들어가 이 규칙이 깨진다. 단계 속성으로 두면 상태와 전이 규칙을 바꾸지 않는다
- 확인을 통과해야 단계가 끝나므로 승인 안내(`/approve`)는 팀장 확인을 통과한 뒤에만 붙는다. Zero는 팀장이 확인한 결과만 승인한다
- QA팀원을 진단 담당으로 두면 기존 흐름(버그 수정, 정기 테스트)에 그대로 들어간다. 테스트 작성 단계는 쓰기 단계가 하나 늘어 흐름이 길어진다

## 규칙

- R6 (새 규칙): `check`는 구현·진단 단계에만 두고, 그 단계 담당(팀원)의 팀장이 맡는다. 담당 자신은 맡지 않는다
- R1 확장: 작성 단계(기획·화면 디자인·설계·구현)의 팀장 확인 담당도 작성 담당으로 본다. 그래서 리뷰 담당은 구현을 확인한 팀장과도 달라야 한다. 지금 구성은 Alpha가 확인하고 Delta가 리뷰하므로 지켜진다
- 팀장 확인은 읽기 전용이다. Codex 엔진 에이전트도 맡을 수 있다

## 트레이드오프

- 호출 수가 늘어난다. 기능 개발은 구현마다 1회 이상, 버그 수정은 진단과 구현마다 1회 이상 늘어난다. 흐름별 예산을 올린다 (기능 개발 25 → 35회, 버그 수정 12 → 18회, 정기 테스트 3 → 6회). Zero가 호출 증가를 받아들였다
- 회사 설정(`~/.zerosync/company/org.yaml`)에 Epsilon과 Zeta가 없으면 기본 파이프라인이 규칙 검사(R4)에 걸려 봇이 시작하지 않는다. 이 변경을 반영할 때 회사 설정에 두 팀원과 인격 파일을 함께 추가한다
- 팀장 확인에서 막히면 `/resume`은 단계를 처음부터 다시 실행한다 (구현은 이미 남긴 커밋 위에서 다시 한다)
- `docs/회사/04-조직.md`의 조직도는 교육 부서 문서 작업이 develop에 들어온 뒤 맞춘다
