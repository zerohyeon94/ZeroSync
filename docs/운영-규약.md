## 1. 역할 (확정, 2026-10-26 ADR-006 반영)

이 장은 [ADR-006](아키텍처%20결정/ADR-006-회사형-구조.md)의 회사 구조를 따른다. 2~4장도 2026-10-26에 같은 기준으로 정리했다. 담당은 파이프라인마다 다를 수 있어 "구현 담당", "리뷰 담당"처럼 역할로 쓰고, 기능 개발 파이프라인의 담당을 괄호로 적는다.

### 1.1 설계 원칙
1. 판단은 Zero만 한다. AI는 제안하고 봇은 전달한다. 방향, 기획 승인, merge, 배포, 문서 반영, 채용은 사람의 명령 없이 진행되지 않는다.
2. 작성자와 검증자를 분리한다. 결과물을 만든 에이전트는 자기 작업을 승인하지 않는다. 리뷰는 만든 에이전트와 다른 에이전트가 구현 대화를 이어받지 않은 새 세션에서 읽기 전용으로 한다.
3. 봇은 LLM이 아니다. 규칙대로만 움직이는 결정론적 프로그램이며, 에이전트 출력의 정해진 블록을 옮길 뿐 해석하지 않는다.
4. 사실은 봇이 확인한다. 테스트 결과처럼 검증 가능한 내용은 봇이 직접 실행한 결과를 공식 기록으로 삼는다.
5. 워크플로 로직은 Discord에 묶이지 않는다. 입출력은 인터페이스 뒤의 discord_io/ 계층과 입력 계층(SPEC 6.5)에만 둔다.
6. 외부(GitHub, Obsidian 볼트)에 쓰는 주체는 봇 하나다. 내용의 출처만 다르다: Zero의 말은 원문 그대로, 에이전트의 말은 정해진 블록 그대로 옮긴다.
7. 판단이 필요한 분류·링크·문서 본문은 에이전트가 제안하고 Zero가 승인한다. 봇은 제안값이 허용 범위 안인지만 검증한다.
8. 조직(팀, 에이전트, 직책)은 설정(`org.yaml`)으로 정하고 Zero만 바꾼다. 에이전트는 채용을 제안할 수 있지만 팀이나 역할을 만들 수 없다 (1.12).

### 1.2 주체와 인격

| 주체 | 인격 | 표시 이름 | 역할 |
|---|---|---|---|
| Zero | ENFJ | (사용자) | 대표. 질문, 결정, 승인, merge, 채용. 유일한 명령 권한자 |
| Beta | INFJ | `[Beta · 기획팀장]` | 기획팀 팀장. 의견(문제·사용자·범위), 기획서, 리뷰(기획서·설계 기준), 문서 반영안 |
| Alpha | INTJ | `[Alpha · 개발팀장]` | 개발팀 팀장. 의견(구조·위험·테스트), 기술 설계, 구현, 리뷰 반영 |
| 봇 | 없음 | `[ZeroSync]` | 호출, 테스트 실행, Issue·push·PR, 볼트 쓰기, 기록, 알림, 예산 집계 |

- 표시 이름은 `[이름 · 직책]`이다. 에이전트의 엔진(Claude, Codex)과 모델은 `org.yaml`에서 정하고 대시보드와 실행 기록에서만 보인다 (SPEC Q16)
- 지금은 모든 에이전트의 엔진이 Claude다. Codex는 설정으로 붙일 수 있으며, 붙이면 리뷰에 먼저 배치한다 (ADR-006 5절)
- 인격은 말투와 관점에만 적용한다. 출력 형식(판정, 의견 블록, 대응 목록)은 인격과 무관하게 고정한다
- 리뷰 담당의 판정 근거는 정확성, 안전성, 테스트 충분성, 기획서·설계와의 일치에 한정한다. 스타일 취향만으로 반려하지 않는다
- 새 팀(디자인, QA, 운영 등)과 팀원은 1.12의 채용으로만 늘어난다. 이름은 그리스 문자 순서(Gamma, Delta, Epsilon …)로 붙인다

### 1.3 권한

권한은 엔진이 아니라 단계별 담당에 붙는다.

| 주체 / 담당 | 파일 | git / GitHub | Discord |
|---|---|---|---|
| Zero | 전체 | 전체 (merge 포함) | 명령어 사용 |
| 봇 | 읽기, SQLite·로그 쓰기, 볼트 허용 경로 쓰기(3.4) | Issue 생성·코멘트·종료, 작업 브랜치 push, draft PR 생성·갱신, PR 코멘트, draft 해제, 볼트 git 자기 파일 커밋 | 게시글·태그 관리, 웹훅 게시 |
| 기획 담당 (PLANNING) | 작업 worktree의 `docs/기획/`만 | 작업 브랜치 로컬 커밋만 | 없음 |
| 설계 담당 (DESIGNING) | 작업 worktree의 `docs/설계/`만 | 작업 브랜치 로컬 커밋만 | 없음 |
| 구현·수정 담당 (IMPLEMENTING, FIXING) | 작업 worktree | 작업 브랜치 로컬 커밋만 | 없음 |
| 의견·리뷰 담당 (OPINIONS, REVIEWING) | 읽기 전용 | 읽기 (diff, log) | 없음 |
| 문서 반영 담당 (DOC_DRAFTING) | 읽기 전용 (수정안은 JSON으로만) | 읽기 | 없음 |

- Codex 러너는 읽기 전용 샌드박스로만 실행되므로, Codex 엔진 에이전트는 읽기 전용 단계(의견, 리뷰)에만 배치할 수 있다

금지 사항
- 모든 에이전트: 자기 작업 승인, main 접근, push, merge, .env 수정, 지정 저장소 밖 접근, 볼트 직접 쓰기, 조직 설정 변경
- 리뷰 담당: 파일 수정, 방향 결정, 직접 구현 (수정 제안은 리뷰 본문 텍스트로만)
- 봇: 내용 판단, 방향 결정, 코드 수정, merge, Zero 외 사용자의 명령 처리(입력 계층의 허용 출처는 SPEC 6.5), 볼트 허용 경로 밖 쓰기

### 1.4 의견 관점

| | Beta · 기획팀장 | Alpha · 개발팀장 |
|---|---|---|
| 관점 | 누구의 어떤 문제인가, 사용 흐름, 범위와 우선순위, 기존 기능·용어와의 일관성 | 구조와 변경 범위, 구현 난이도, 실행 위험, 엣지 케이스, 테스트 방법, 더 단순한 대안 |
| 기본 질문 | 이것을 써야 하는가, 어디까지 할 것인가 | 만들 수 있는가, 왜 실패할 수 있나, 더 작게 할 수 있나 |

- 팀장별 역량 전체는 ADR-006 2절과 인격 파일(`agents/<이름>.md`)에 둔다

### 1.5 단계별 담당 (기능 개발 파이프라인)

파이프라인마다 단계와 담당, 승인 게이트를 YAML로 선언한다 (SPEC 3장, Q13). 아래는 기본 파이프라인인 기능 개발의 담당이다. 다른 파이프라인은 자기 선언을 따른다.

| 단계 | 담당 | 입력 | 산출물 |
|---|---|---|---|
| OPINIONS | Beta, Alpha 병렬 | 아이디어 원문 + 저장소 | 각자 의견 |
| DEBATE (선택) | 둘 다 1회 | 상대 의견 | 반박 또는 동의 |
| DECIDED | Zero → 봇 | 의견들 | `/decide <방향>`, GitHub Issue, 볼트 결정 노트·논의 목록 행 |
| PLANNING | Beta | 결정 원문 + 기능 노트 목록 | 기획서(앱 저장소 `docs/기획/`) + 요약 JSON(변경 유형·대상 기능·완료 기준 포함) |
| (기획 승인) | Zero `/approve` | 기획 요약 | 결정 노트에 변경 유형·대상 기능·기획 링크 반영 |
| DESIGNING | Alpha | 승인된 기획서 + 저장소 | 설계 문서(앱 저장소 `docs/설계/`) + 요약 JSON(변경 범위·테스트 계획·위험) |
| IMPLEMENT | Alpha → 봇 테스트 | 기획서 + 설계 | 커밋 + 봇 테스트 결과 |
| REVIEW | Beta (새 세션, 읽기 전용) | diff + 기획·설계 요약 + 봇 테스트 결과 | 판정 + 지적 목록 |
| FIX | Alpha → 봇 테스트 | [필수] 지적 목록 | 수정 커밋 + 항목별 대응 |
| MERGE | Zero (GitHub) | PR | develop에 merge commit. 봇이 PR 상태 조회로 감지하고 Issue 종료 |
| DOC_SYNC | Beta 제안 → Zero 승인 → 봇 쓰기 | merge된 코드 + 기능 노트·허브 원문 + 결정 노트 | 기능 정의서 생성·갱신, 허브 기능 지도 갱신 |
| DONE | 봇 | | 결정 노트·논의 목록 완료 처리 |

- 기획 승인 뒤 설계는 Zero 승인 없이 구현으로 이어진다. Zero는 설계 요약을 알림 없이 받아 보고, 필요하면 `/stop`이나 리뷰 단계에서 개입한다
- 유지보수처럼 작은 작업용 파이프라인은 PLANNING을 뺄 수 있다. 이때는 DESIGNING 뒤에 Zero 승인 게이트를 둔다. 어떤 파이프라인이든 구현 단계 앞에 승인 게이트가 최소 1개 있어야 한다 (SPEC 3장 규칙 검사)
- QA팀을 채용하면 REVIEW 담당을 QA로 바꾼다 (ADR-006 5절)

### 1.6 OPINIONS 단계의 추가 질문
- 게시글에 일반 메시지: 의견을 내는 팀장 모두 응답
- `@beta ...` / `@alpha ...`: 지정된 팀장만 응답 (에이전트 이름 기준. 채용하면 `@gamma` 등이 추가된다)
- `/debate`: Zero의 새 질문 없이 서로의 의견에 반박 1회
- 첫 의견은 서로의 의견을 보지 않고 독립 작성. 두 번째 질문부터는 게시글 전체 흐름을 전달
- 맥락은 봇이 SQLite 기록으로 매번 재구성해 전달한다 (CLI 세션 이어가기는 최적화 수단)
- 질문 횟수 제한 없음. 5회를 넘으면 봇이 "/decide 대기 중" 한 줄 알림
- 상태는 `/decide` 전까지 OPINIONS 유지
- 팀이 늘면 의견을 낼 팀을 파이프라인마다 선언한다

### 1.7 테스트
- 봇이 projects.yaml의 test 명령을 전역 락 아래에서 실행한다
  - 이유: 에이전트의 자기 보고 대신 봇이 직접 확인한 결과를 공식 기록으로 삼는다. 읽기 전용 샌드박스에서는 xcodebuild(DerivedData·시뮬레이터 쓰기)가 실패할 수 있다
- 결과(종료 코드, 통과/실패 수, 실패 테스트명, 소요 시간)를 요약하고 전체 로그는 파일로 저장한다
- 테스트 실패 시 리뷰 담당을 호출하지 않고 바로 구현 담당에게 FIX 요청 (사용량 절약)
- 테스트 실패 재시도 횟수는 리뷰 라운드 제한과 별도로 센다 (2회 초과 시 NEEDS_HUMAN, SPEC Q2)
- 리뷰 담당은 테스트 결과를 입력으로 받아 판정한다: 변경을 검증하는 테스트의 존재, 엣지 케이스 누락, 코드 결함, 기획서 완료 기준 충족

### 1.8 GitHub Issue
- 생성 시점: Zero의 `/decide` 직후. 의견 단계에서 버려진 아이디어는 Issue를 만들지 않는다 (Discord에만 기록)
- 위치: 각 앱 저장소 (예: GagaeSsi)
- 내용은 봇이 기존 텍스트를 조립한다. 에이전트를 별도로 호출하지 않는다
  - 이유: 결정은 Zero의 원문 그대로 남아야 하고, 추가 호출 비용을 피하며, 작업 정의는 기획 단계에서 이미 작성된다

| 항목 | 출처 |
|---|---|
| 제목 | Discord 게시글 제목 (다른 입력 경로는 요청 제목) |
| 결정 | Zero의 /decide 원문 |
| 배경 | Zero의 아이디어 원문 |
| 의견 요약 | 팀장 의견의 stance·conclusion과 risks |
| 링크 | Discord 게시글 |

- PLANNING·DESIGNING 완료 시 봇이 기획·설계 요약을 Issue 코멘트로 추가한다
- 브랜치명에 Issue 번호를 포함한다 (예: `feat/42-budget-banner`, 4.2 참고)
- develop merge는 자동 종료(`Closes`)가 동작하지 않으므로, 봇이 merge 감지 시 코멘트를 남기고 Issue를 직접 종료한다 (4.6 참고)
- 예외 처리

| 상황 | 처리 |
|---|---|
| /decide 전 /stop | Issue 없음 |
| /decide 후 /stop | 중지 사유를 코멘트로 남기고 "not planned"로 종료 |
| NEEDS_HUMAN | Issue 유지, `needs-human` 라벨 추가 |

### 1.9 GitHub PR
- 내용은 에이전트가 만들고, GitHub에 쓰는 작업은 모두 봇이 한다
- PR 항목별 작성자

| 항목 | 작성자 | 출처 |
|---|---|---|
| 제목 | 봇 | 작업 제목 + 접두어 |
| 결정 | 봇 | Zero의 /decide 원문 |
| 기획 요약 | 봇 | 기획 요약 JSON |
| 변경 요약, 설계 의도, 확인할 점 | 구현 담당 (Alpha) | 구현 완료 시 요약 블록 |
| 테스트 | 봇 | 봇 실행 결과 |
| 리뷰 이력 | 봇 | 라운드별 판정 요약 |
| Discord 링크, 브랜치, Refs #Issue | 봇 | 작업 정보 |

- 리뷰 본문은 PR 코멘트로 라운드마다 추가한다. 작성자 표시는 `[이름 · 직책]`이다
- PR 본문은 FIX가 끝날 때마다 봇이 갱신한다
- 처음부터 draft로 생성하고, 리뷰 담당이 APPROVED를 내면 봇이 draft를 해제한다
- merge는 Zero가 직접 한다

### 1.10 기록의 역할 분담
- Discord 게시글: 논의 과정 전체 (의견, 추가 질문, 반박)
- GitHub Issue: 무엇을 왜 하기로 했는가 (결정)
- GitHub PR: 어떻게 만들었고 어떻게 검증했는가 (구현, 리뷰)
- 앱 저장소 `docs/기획/`, `docs/설계/`: 기획서와 설계 전문
- Obsidian 볼트: 결정 노트, 논의 목록, 기능 정의서 (상세는 3장)
- 조직과 채용 기록: 비공개 회사 저장소의 `org.yaml` (SPEC Q12, Q17)

### 1.11 인터페이스 채널
- 논의와 승인은 Discord에서 한다 (모바일 입력, 푸시 알림, 외부에서 맥으로의 중계, 무제한 기록을 별도 구현 없이 확보)
- 여러 프로젝트·파이프라인의 현황과 지표는 로컬 대시보드에서 본다. 대시보드는 SQLite를 읽기 전용으로 읽는다
- Discord 외 입력(Slack, Jenkins, 테스트 베드 SSH)은 입력 계층으로 받는다 (SPEC 6.5)
- 봇 토큰은 앱에 넣지 않으며, 개인 계정 토큰 사용(셀프봇)은 하지 않는다

### 1.12 채용

새 팀과 팀원이 필요한 시점은 팀장이 먼저 알아채고 제안한다. 채용 여부와 설정 변경은 Zero가 한다.

- 새 팀 제안: 자기 팀 역량 밖의 일이 반복될 때 (예: 화면 설계 → 디자인팀, 리뷰가 코드 품질에 미치지 못함 → QA팀, 운영 요청이 개발을 밀어냄 → 운영팀)
- 팀원 제안: 의견의 폭이 부족해 다른 관점이 더 필요할 때, 특정 업무를 실제로 맡을 담당이 필요할 때
- 제안 방법: 작업 보고 JSON의 선택 필드 `hiring_proposal`로 붙인다. 제안만 하는 실행은 만들지 않는다 (SPEC Q19)
- 제안 내용: 근거(어떤 작업에서 무엇이 부족했는지), 맡길 업무, 원하는 성격(MBTI)·역량, 채용하지 않을 때의 영향. 대기 시간·실패 수·한도 초과 수 같은 숫자 근거는 봇이 DB에서 계산해 붙인다
- Zero의 답: `/hire`로 수락 또는 거절한다. 수락하면 Zero가 `org.yaml`과 인격 파일을 추가한다. 거절 기록은 다음 프롬프트에 넣어, 새 근거가 생기기 전까지 같은 제안을 반복하지 않게 한다
- 채용 기록(이름, 팀, 직책, 엔진, 성격, 역량, 채용일, 제안한 팀장, 근거)은 `org.yaml`과 ZeroSync 개발 일지에 남긴다

## 2. Discord 대화 형태 (확정)

### 2.1 공통: 에이전트 출력 방식 (확정)
- 에이전트는 미리 정한 JSON 스키마로 출력한다
- 봇은 JSON을 추출해 pydantic 스키마로 검증한 뒤 SQLite에 원본을 저장하고, render 계층에서 Discord 메시지로 변환해 게시한다
- 저장, Discord 표시, Issue·PR·볼트 옮겨 적기는 모두 같은 JSON에서 나온다. 표시 방식 변경은 render 계층만 수정한다
- CLI의 스키마 강제 출력 옵션을 우선 사용하고, 없으면 프롬프트로 JSON 코드 블록을 요청해 추출한다 [검증 필요]
- 검증 실패 시 오류 내용을 붙여 1회 재요청한다. 다시 실패하면 원문을 "형식 오류" 표시와 함께 게시하고 Zero에게 알린다

### 2.2 의견 형식 (확정)
- 필드 4개: 결론 / 근거 / 위험 / 제안 ("질문" 필드는 두지 않음)
- 입장(stance)은 4개 값으로 고정: 찬성 / 조건부 찬성 / 반대 / 대안 제시
- 위험은 찬성이어도 최소 1개 이상 필수 (AI가 찬성 시 단점을 생략하는 경향 방지)

| 필드 | 키 | 제약 |
|---|---|---|
| 입장 | stance | 4개 값 중 하나 |
| 결론 | conclusion | 한 줄, 120자 이내 |
| 근거 | reasons | 1~4개 |
| 위험 | risks | 1~3개 |
| 제안 | proposal | 300자 이내 |

### 2.3 리뷰 판정 형식 (확정)
- 지적은 두 등급으로 구분한다: [필수] / [권장]

| 등급 | 해당하는 경우 |
|---|---|
| [필수] | 버그, 데이터 손실·보안 위험, 기획서·설계와 다른 동작, 기획서 완료 기준 미충족, 변경을 검증하는 테스트 누락, 빌드·테스트를 깨뜨리는 문제 |
| [권장] | 가독성, 이름, 중복 제거, 더 나은 구조, 현재 문제가 없는 성능 개선 |

- 판정 규칙: [필수]가 있으면 CHANGES_REQUESTED, 없으면 APPROVED
- 판정과 지적 등급이 어긋나면 봇이 형식 오류로 처리한다 (스키마 검증으로 강제)
- 필드: verdict, summary(200자), findings 최대 10개 (severity, file, line, problem, reason, suggestion)
- CHANGES_REQUESTED 시 구현 담당(기능 개발은 Alpha)에게 [필수] 항목을 FIX 대상으로 전달한다. [권장]은 참고로 함께 주되 반영 여부는 구현 담당 재량
- APPROVED 후 남은 [권장] 항목은 PR 코멘트로 남기고, 처리 여부는 Zero가 결정한다 (예: merge 전 `/fix 권장 반영`으로 1회 추가 수정)
- APPROVED 시 봇이 Discord에 남은 [권장] 개수를 표시한다
- 2라운드부터 리뷰 담당(기능 개발은 Beta)은 이전 라운드 [필수] 항목의 해결 여부를 항목별로 확인한다 (등급 하향으로 문제를 놓치는 위험 보완)

### 3.8 변경 유형
- `change_type`과 `target_feature`는 파이프라인의 첫 문서 단계 담당이 JSON으로 제안하고(기능 개발은 Beta의 기획 JSON, 기획 단계가 없으면 설계 JSON), 그 단계의 `/approve`로 함께 승인된다 (SPEC 5.4)
- 봇은 enum 값과 `target_feature`가 실제 `기능/` 폴더의 파일명인지 검증한다. 제안하는 담당에게는 봇이 해당 프로젝트 `기능/` 파일 목록을 전달한다

| change_type | 의미 | DOC_SYNC에서 |
|---|---|---|
| 기능 추가 | 새 기능 | 새 기능 정의서 생성 + 허브 기능 지도에 행 추가 |
| 기능 변경 | 기존 기능 동작 변경 | 기존 기능 정의서 본문 수정 + 확인 이력 + 허브 행 수정(필요 시) |
| 버그 수정 | 의도대로 고침 | 확인 이력 + 필요 시 예외·코드 근거 수정 |
| 내부 개선 | 동작 동일 | 확인 이력 + 필요 시 코드 근거 수정 |

### 3.9 DOC_SYNC (merge 후 문서 반영)
1. 봇이 진행 중인 PR 상태를 주기적으로 조회해 merge를 감지한다 (예: 5분 간격. 맥은 외부 접속 불가이므로 webhook 대신 조회)
2. 봇이 문서 반영 담당(기능 개발은 Beta)을 읽기 전용으로 호출한다. 입력: merge된 develop 코드, 대상 기능 노트·허브 원문, 결정 노트, 볼트 기능 노트 형식
3. 문서 반영 담당은 수정안 JSON을 출력한다: 파일별 {path, action(create/update), content(전체 내용)}
   - 기능 노트 형식(이 기능이 하는 일 / 현재 처리 흐름 / 예외와 지켜야 할 조건 / 개선 가설과 확인 조건 / 연결 기술 / 코드와 기획 근거 / 확인 이력)을 유지한다
   - 확인 이력에 한 줄 추가: 날짜, PR, 봇 테스트 결과. 실기기·배포는 확인 범위가 아님을 명시
   - status는 "코드확인". 출시 완료로 표기하지 않는다
   - 결정 노트로 가는 링크를 포함한다
4. 봇 검증: 경로가 쓰기 허용 범위인지, frontmatter 필수 키 유지, 대상 파일 존재 여부(update는 존재, create는 미존재)
5. 봇이 Discord에 요약 + diff 파일을 첨부하고 Zero를 멘션한다
6. Zero 명령
   - `/approve`: 봇이 파일을 쓰고 볼트 git에 커밋한다
   - `/revise <요청>`: 문서 반영 담당이 수정안을 다시 작성한다
   - `/skip`: 기능 정의서·허브는 그대로 두고 결정 노트만 완료 처리한다
7. 승인 시점에 대상 파일의 해시가 수정안 생성 시점과 다르면(Zero가 그사이 직접 편집) 쓰지 않고 수정안을 다시 만든다
8. 완료 후 결정 노트 zerosync_status=doc_synced, 논의 목록 상태 "완료"

### 3.10 볼트 git (Obsidian 볼트 저장소 전용. 앱 저장소 커밋은 4.4)
- 볼트는 여러 프로젝트가 한 저장소에 있으므로 scope에 프로젝트 슬러그를 쓴다 (gagaessi, focus, jday)
- 볼트 규칙의 `git add -A` 대신, 봇은 자기가 쓴 파일만 `git add <경로>`로 지정해 항목별로 커밋한다 (Zero가 편집 중인 노트가 섞이지 않게)
- 볼트 규칙 문서에 "ZeroSync 봇은 자기 파일만 커밋" 예외를 추가한다 (Zero가 직접 또는 별도 요청으로)
- 커밋 메시지: 제목 `docs(<프로젝트 슬러그>): ZeroSync <결정|기획 승인|설계 승인|기능|중단> - <제목>`, 본문 "확인: … / 아직 아님: …", 꼬리말 `ZeroSync-Task: <project>-<Issue번호>`, `Refs: <Issue 또는 PR URL>`
- 커밋 경로 지정: `git add -- <경로>` 후 `git commit -- <경로>` (다른 스테이징 파일이 섞이지 않게)
- 볼트 규칙 예외 문구(봇은 자기 파일만 커밋)는 저장소 연결 후 에이전트가 수정안을 만들고 Zero가 승인한다
- iCloud 동기화 중 쓰기 실패 시 짧게 재시도하고, 계속 실패하면 #zerosync-ops에 알린다 [검증 필요]
- 볼트 루트가 git 저장소인지, 봇 실행 계정에서 접근 가능한지 [검증 필요]

## 4. GitHub 규칙 (앱 저장소, 확정)

### 4.1 브랜치 전략 (Git Flow)
- `main`: 배포 버전 기준. 봇은 main을 읽지도 쓰지도 않는다. develop → main 릴리스는 Zero가 직접 한다
- `develop`: 기능 개발 후 확인·테스트 브랜치. 모든 작업 브랜치의 생성 기준이자 PR 대상
- 작업 브랜치: 기능마다 새로 만든다. 모든 프로젝트(가게씨, 오롯, 제이데이) 공통
- ZeroSync 저장소(봇 자체 개발)도 develop 기준으로 작업 브랜치를 만들고, 스레드당 develop 대상 draft PR을 연다. develop → main 릴리스는 Zero가 직접 한다. 세부 규칙은 저장소의 AGENTS.md를 따르며 이 장의 나머지 항목(봇 자동화)과는 별개다 (2026-10-05 변경, 이전: main 기준)

### 4.2 브랜치 이름
- 형식: `<type>/<Issue번호>-<slug>` (예: `feat/42-budget-banner`). `claude/` 접두어는 쓰지 않는다
- type은 승인된 변경 유형(3.8)으로 결정한다

| 변경 유형 | type |
|---|---|
| 기능 추가, 기능 변경 | feat |
| 버그 수정 | fix |
| 내부 개선 | refactor |

- slug는 첫 문서 단계 담당이 JSON에 제안하고(기능 개발은 기획 JSON) 봇이 형식만 검증한다: `^[a-z0-9]+(-[a-z0-9]+){0,4}$`, 40자 이내

### 4.3 브랜치 생성 순서
1. 봇이 develop 최신 커밋에서 worktree를 만든다 (브랜치 이름 없이 detached 상태)
2. 첫 문서 단계 담당이 문서를 작성·커밋하고 JSON(change_type, slug 포함)을 출력한다. 기능 개발은 Beta가 `docs/기획/<Issue번호>-<slug>.md`를 쓴다
3. 봇이 JSON을 검증하고 브랜치 이름을 정해 현재 커밋에 브랜치를 만든 뒤 push한다
4. 승인 전 수정(`/revise`)으로 변경 유형이 바뀌면 봇이 새 이름으로 push하고 이전 원격 브랜치를 삭제한다 (PR 생성 전이므로 영향 없음)

### 4.4 앱 저장소 커밋 메시지
- 형식: `<type>(<영역>): <요약>` + 빈 줄 + 본문(선택) + 꼬리말 `Refs: #<Issue번호>`
- 단일 프로젝트 저장소이므로 scope에 프로젝트명을 쓰지 않는다. scope는 앱 내부 영역(budget, spend, settings 등)이며 애매하면 생략한다
- type: feat / fix / refactor / test / docs / chore
- merge commit 방식이므로 모든 커밋이 develop 이력에 남는다. 커밋 단위 예시

| 커밋 | 예시 |
|---|---|
| 기획서 | `docs(plan): 예산 초과 배너 기획` |
| 설계 문서 | `docs(design): 예산 초과 배너 설계` |
| 구현 (논리 단위) | `feat(budget): 월 지출 합계 캐시 추가` |
| 테스트 | `test(budget): 월 경계 시간대 테스트 추가` |
| 리뷰 반영 | `fix(budget): 리뷰 1라운드 [필수] 1·2 반영` |

- `wip`, `수정` 같은 의미 없는 메시지 금지
- 봇은 push 전에 커밋 메시지 형식을 정규식으로 검사하고, 틀리면 push 전에 커밋한 담당 에이전트에게 수정을 요청한다 (push 전이므로 이력 수정 허용)
- push 후에는 force push 금지. 리뷰 반영은 항상 새 커밋으로 추가한다

### 4.5 PR
- 대상: develop. 처음부터 draft로 생성하고 리뷰 담당의 APPROVED 시 draft 해제 (1.9 참고)
- 제목: `<type>(<영역>): <요약>` (예: `feat(budget): 월 예산 초과 시 홈 화면 배너 표시`)
- 본문 꼬리에 `Refs #<Issue번호>` (develop merge에서는 Closes가 동작하지 않으므로 사용하지 않음)

### 4.6 merge와 정리
- merge 방식: Merge commit (작업 브랜치의 모든 커밋이 develop에 보이고, merge 커밋이 기능 단위 경계를 남김. 되돌릴 때 `git revert -m 1 <merge커밋>`)
- merge는 Zero가 GitHub에서 직접 한다
- 봇이 PR 상태 조회로 merge를 감지하면: Issue에 "develop merge 완료" 코멘트 후 Issue 종료 → DOC_SYNC 시작
- 저장소 설정 "Automatically delete head branches"를 켜서 원격 작업 브랜치를 자동 삭제한다
- 맥의 worktree는 DOC_SYNC 완료 후 봇이 정리한다

### 4.7 봇의 push 보호
- 두 조건을 모두 만족할 때만 push한다
  1. 브랜치 이름이 `^(feat|fix|refactor)/\d+-[a-z0-9]+(-[a-z0-9]+)*$` 형식 (main, develop은 형식에서 제외됨)
  2. 해당 작업에서 봇이 만든 브랜치로 SQLite에 기록된 이름과 일치 (Zero가 직접 만든 같은 형식의 브랜치는 건드리지 않음)
- GitHub 브랜치 보호(rulesets)로 main·develop 직접 push 금지를 함께 건다 [검증 필요: 개인 private 저장소 요금제에서 사용 가능 여부]

### 4.8 라벨
| 라벨 | 대상 | 시점 |
|---|---|---|
| `zerosync` | Issue, PR | 생성 시 |
| `type:feature` / `type:fix` / `type:refactor` | Issue, PR | 변경 유형 승인 시 (기획 승인, 기획 단계가 없으면 설계 승인) |
| `needs-human` | Issue, PR | NEEDS_HUMAN 진입 시, 해결되면 제거 |

- 봇이 처음 실행될 때 저장소에 라벨이 없으면 만든다
