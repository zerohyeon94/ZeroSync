## 1. 역할 (확정, 2026-10-28 ADR-007 반영)

이 장은 [ADR-006](아키텍처%20결정/ADR-006-회사형-구조.md)과 [ADR-007](아키텍처%20결정/ADR-007-회사-재정의.md)의 회사 구조를 따른다. 회사는 교육·비서·제품 세 부서이고, 이 규약은 지금 제품 부서를 다룬다 ([회사 재정의 문서](회사/README.md)). 2~4장도 같은 기준으로 정리했다. 담당은 파이프라인마다 다를 수 있어 "구현 담당", "리뷰 담당"처럼 역할로 쓰고, 기능 개발 파이프라인의 담당을 괄호로 적는다.

### 1.1 설계 원칙
1. 판단은 Zero만 한다. AI는 제안하고 봇은 전달한다. 방향, 기획 승인, merge, 배포, 문서 반영, 채용은 사람의 명령 없이 진행되지 않는다.
2. 작성자와 검증자를 분리한다. 결과물을 만든 에이전트는 자기 작업을 승인하지 않는다. 리뷰는 만든 에이전트와 다른 에이전트가 구현 대화를 이어받지 않은 새 세션에서 읽기 전용으로 한다.
3. 봇은 LLM이 아니다. 규칙대로만 움직이는 결정론적 프로그램이며, 에이전트 출력의 정해진 블록을 옮길 뿐 해석하지 않는다.
4. 사실은 봇이 확인한다. 테스트 결과처럼 검증 가능한 내용은 봇이 직접 실행한 결과를 공식 기록으로 삼는다.
5. 워크플로 로직은 Discord에 묶이지 않는다. 입출력은 인터페이스 뒤의 discord_io/ 계층에만 둔다. 입력은 Discord와 봇 일정뿐이다 (SPEC 6.5).
6. 외부(GitHub, Obsidian 볼트)에 쓰는 주체는 봇 하나다. 내용의 출처만 다르다: Zero의 말은 원문 그대로, 에이전트의 말은 정해진 블록 그대로 옮긴다.
7. 판단이 필요한 분류·링크·문서 본문은 에이전트가 제안하고 Zero가 승인한다. 봇은 제안값이 허용 범위 안인지만 검증한다.
8. 조직(팀, 에이전트, 직책)은 설정(`org.yaml`)으로 정하고 Zero만 바꾼다. 에이전트는 채용을 제안할 수 있지만 팀이나 역할을 만들 수 없다 (1.12).

### 1.2 주체와 인격

| 주체 | 인격 | 표시 이름 | 역할 |
|---|---|---|---|
| Zero | ENFJ | (사용자) | 대표 겸 제품 부서장. 질문, 결정, 승인, merge, 스토어 제출, 채용. 유일한 명령 권한자 |
| Beta | INFJ | `[Beta · 기획팀장]` | 기획팀 팀장. 채팅 의견(문제·사용자·범위), 기획서, 문서 반영안. 배포 업무 겸임(출시 준비) |
| Gamma | ISFP | `[Gamma · 디자인팀장]` | 디자인팀 팀장. 화면 디자인(명세, Claude 디자인), 제품 디자인 시스템 유지 (2026-10-28 채용) |
| Alpha | INTJ | `[Alpha · 개발팀장]` | 개발팀 팀장. 채팅 의견(구조·위험·테스트), 기술 설계, 개발팀원의 구현·수정 확인 |
| Delta | ISTJ | `[Delta · QA팀장]` | QA팀 팀장. 검증(리뷰), QA팀원의 진단 확인 (2026-10-28 채용) |
| Epsilon | ISTP | `[Epsilon · 개발팀원]` | 개발팀 팀원. 승인된 설계대로 구현, 테스트 실패·지적 수정 (2026-10-28 채용, ADR-008) |
| Zeta | INTP | `[Zeta · QA팀원]` | QA팀 팀원. 버그 진단, 정기 테스트 실패 진단 (2026-10-28 채용, ADR-008) |
| 봇 | 없음 | `[ZeroSync]` | 호출, 테스트 실행, Issue·push·PR, 볼트 쓰기, 기록, 알림, 보고, 예산 집계 |

- 제품 부서의 팀장은 모두 Zero에게 직접 보고한다. 교육·비서 부서는 담당 에이전트와 Zero의 1대1이며 그 부서를 시작할 때 정한다 (ADR-007)
- 표시 이름은 `[이름 · 직책]`이다. 에이전트의 엔진(Claude, Codex)과 모델은 `org.yaml`에서 정하고 대시보드와 실행 기록에서만 보인다 (SPEC Q16)
- 지금은 모든 에이전트의 엔진이 Claude다. Codex는 설정으로 붙일 수 있으며, 붙이면 리뷰(Delta)에 먼저 배치한다 (ADR-006 5절)
- 인격은 말투와 관점에만 적용한다. 출력 형식(판정, 의견 블록, 대응 목록)은 인격과 무관하게 고정한다
- 리뷰 담당의 판정 근거는 정확성, 안전성, 테스트 충분성, 기획서·설계와의 일치에 한정한다. 스타일 취향만으로 반려하지 않는다
- 팀장은 무엇을·어떤 기준으로 할지 정하고, 팀원은 그대로 실행한다. 팀원의 결과는 같은 팀 팀장이 확인한 뒤에 다음 단계로 간다(팀장 확인). 지적이 있으면 팀원이 고치고 다시 확인을 받으며, 2회 안에 통과하지 못하면 Zero에게 넘긴다 (ADR-008)
- 새 팀과 팀원은 1.12의 채용으로만 늘어난다. 이름은 그리스 문자 순서로 붙인다. Gamma(디자인), Delta(QA), Epsilon(개발팀원), Zeta(QA팀원) 다음은 Eta다

### 1.3 권한

권한은 엔진이 아니라 단계별 담당에 붙는다.

| 주체 / 담당 | 파일 | git / GitHub | Discord |
|---|---|---|---|
| Zero | 전체 | 전체 (merge 포함) | 명령어 사용 |
| 봇 | 읽기, SQLite·로그 쓰기, 볼트 허용 경로 쓰기(3.4) | Issue 생성·코멘트·종료, 작업 브랜치 push, draft PR 생성·갱신, PR 코멘트, draft 해제, 볼트 git 자기 파일 커밋 | 게시글·태그 관리, 웹훅 게시 |
| 기획 담당 (PLANNING) | 작업 worktree의 `docs/기획/`만 | 작업 브랜치 로컬 커밋만 | 없음 |
| 디자인 담당 (UI_DESIGNING) | 작업 worktree의 `docs/디자인/`만. Claude 디자인 생성 (SPEC V14) | 작업 브랜치 로컬 커밋만 | 없음 |
| 설계 담당 (DESIGNING) | 작업 worktree의 `docs/설계/`만 | 작업 브랜치 로컬 커밋만 | 없음 |
| 구현·수정 담당 (IMPLEMENTING, FIXING) | 작업 worktree | 작업 브랜치 로컬 커밋만 | 없음 |
| 채팅 답·리뷰·진단 담당 (대화, REVIEWING, DIAGNOSING) | 읽기 전용 | 읽기 (diff, log) | 없음 |
| 문서 반영·출시 준비 담당 (DOC_DRAFTING, RELEASE_PREPARING) | 읽기 전용 (결과는 JSON으로만) | 읽기 | 없음 |

- Codex 러너는 읽기 전용 샌드박스로만 실행되므로, Codex 엔진 에이전트는 읽기 전용 일(채팅 답, 리뷰, 진단)에만 배치할 수 있다

금지 사항
- 모든 에이전트: 자기 작업 승인, main 접근, push, merge, .env 수정, 지정 저장소 밖 접근, 볼트 직접 쓰기, 조직 설정 변경, 스토어 제출, 외부로 글 보내기, 비용 지출, 메일 접근
- 리뷰 담당: 파일 수정, 방향 결정, 직접 구현 (수정 제안은 리뷰 본문 텍스트로만)
- 봇: 내용 판단, 방향 결정, 코드 수정, merge, 스토어 제출, Zero 외 사용자의 명령 처리, 볼트 허용 경로 밖 쓰기

### 1.4 의견 관점

의견은 제품 채팅 채널의 대화에서 낸다 (1.6).

| | Beta · 기획팀장 | Gamma · 디자인팀장 | Alpha · 개발팀장 | Delta · QA팀장 |
|---|---|---|---|---|
| 관점 | 누구의 어떤 문제인가, 사용 흐름, 범위와 우선순위, 기존 기능·용어와의 일관성 | 화면 구성, 상태(빈 화면·로딩·오류·큰 글씨), 디자인 시스템과의 일관성, 플랫폼 규칙 | 구조와 변경 범위, 구현 난이도, 실행 위험, 엣지 케이스, 테스트 방법, 더 단순한 대안 | 확인 기준, 빠진 경우, 회귀 위험, 테스트로 확인할 방법 |
| 기본 질문 | 이것을 써야 하는가, 어디까지 할 것인가 | 사용자가 화면에서 헤매지 않는가 | 만들 수 있는가, 왜 실패할 수 있나, 더 작게 할 수 있나 | 무엇을 보면 됐다고 할 수 있나 |

- 팀장별 역량 전체는 ADR-006 2절(Beta, Alpha), [회사 재정의 04-조직](회사/04-조직.md) 3장(Gamma, Delta)과 인격 파일(`agents/<이름>.md`)에 둔다
- Gamma와 Delta는 채팅에서 불렀을 때만 답한다. 아무도 부르지 않으면 Beta와 Alpha가 답한다 (1.6)

### 1.5 단계별 담당 (기능 개발 파이프라인)

파이프라인마다 단계와 담당, 승인 게이트를 YAML로 선언한다 (SPEC 3장, Q13). 아래는 기본 파이프라인인 기능 개발의 담당이다. 버그 수정, 출시, 정기 테스트는 1.5-1과 각자의 선언을 따른다.

| 단계 | 담당 | 입력 | 산출물 |
|---|---|---|---|
| 대화 (채팅) | 부른 팀장, 아무도 안 부르면 Beta·Alpha | Zero의 메시지 + 최근 대화 + 저장소 | 각자 의견 |
| DEBATE (선택) | 직전에 답한 두 팀장 1회씩 | 상대 의견 | 반박 또는 동의 |
| 시작 | Zero → 봇 | 채팅의 의견들 | `/task feature <제목>`, 포럼 포스트(의견 요약), GitHub Issue, 볼트 결정 노트·논의 목록 행 |
| PLANNING | Beta | 결정 원문 + 기능 노트 목록 | 기획서(앱 저장소 `docs/기획/`) + 요약 JSON(변경 유형·대상 기능·완료 기준·화면 변경 여부 포함) |
| (기획 승인) | Zero `/approve` | 기획 요약 | 결정 노트에 변경 유형·대상 기능·기획 링크 반영 |
| UI_DESIGNING | Gamma (화면 변경이 있을 때만) | 승인된 기획서 + 제품 디자인 시스템 | 디자인 명세(앱 저장소 `docs/디자인/`) + Claude 디자인 링크 + 요약 JSON |
| (디자인 승인) | Zero `/approve` | 디자인 요약과 링크 | 결정 노트에 디자인 링크 반영 |
| DESIGNING | Alpha | 승인된 기획서·디자인 명세 + 저장소 | 기술 설계 문서(앱 저장소 `docs/설계/`) + 요약 JSON(변경 범위·테스트 계획·위험) |
| IMPLEMENT | Epsilon → Alpha 확인 → 봇 테스트 | 기획서 + 디자인 명세 + 설계 | 커밋 + 팀장 확인 판정 + 봇 테스트 결과. 확인에서 [필수] 지적이 나오면 Epsilon이 고치고 다시 확인한다 (ADR-008) |
| REVIEW | Delta (새 세션, 읽기 전용) | diff + 기획·디자인·설계 요약 + 봇 테스트 결과 | 판정 + 지적 목록 |
| FIX | Epsilon → Alpha 확인 → 봇 테스트 | [필수] 지적 목록 또는 테스트 실패 | 수정 커밋 + 항목별 대응 + 팀장 확인 판정 |
| MERGE | Zero (GitHub) | PR | develop에 merge commit. 봇이 PR 상태 조회로 감지하고 Issue 종료 |
| DOC_SYNC | Beta 제안 → Zero 승인 → 봇 쓰기 | merge된 코드 + 기능 노트·허브 원문 + 결정 노트 | 기능 정의서 생성·갱신, 허브 기능 지도 갱신 |
| DONE | 봇 | | 결정 노트·논의 목록 완료 처리 |

- 기술 설계는 Zero 승인 없이 구현으로 이어진다. Zero는 설계 요약을 알림 없이 받아 보고, 필요하면 `/stop`이나 리뷰 단계에서 개입한다
- 화면이 바뀌지 않는 기능(기획 요약의 화면 변경 없음)은 UI_DESIGNING과 디자인 승인을 건너뛴다 (ADR-007)
- 어떤 파이프라인이든 구현 단계 앞에 승인 게이트가 최소 1개 있어야 한다 (SPEC 3장 규칙 검사)

### 1.5-1 다른 파이프라인의 담당 (ADR-007)

| 파이프라인 | 시작 | 단계와 담당 |
|---|---|---|
| 버그 수정 | `/task bug` | 진단 Zeta(Delta 확인) → [Zero 수정 방향 승인] → 수정 Epsilon(Alpha 확인) → 봇 테스트 → 검증 Delta → [Zero merge]. 문서 반영은 하지 않는다 (기능 정의서 변경은 `/task feature`) |
| 출시 | `/release <버전>` | 봇 전체 테스트·빌드 → 출시 준비 Beta(점검 목록, 버전, 릴리스 노트·스토어 설명 초안, 인증서 만료 확인) → [Zero 출시 승인] → Zero가 직접 스토어 제출 |
| 정기 테스트 | 봇 일정 | 봇 테스트 → 실패 때만 진단 Zeta(Delta 확인) → 포럼 보고 포스트. 수정은 Zero가 `/task bug`로 시작 |
| 아이디어 관리 | `/idea` | 봇이 아이디어 목록에 기록 |

### 1.6 대화 (제품 채팅 채널, ADR-007)
- 의견은 제품마다 있는 채팅 채널(`#<제품>-chat`)에서 나눈다. 포럼에는 의견 단계가 없다
- 일반 메시지: Beta와 Alpha가 답한다
- `@beta ...` / `@gamma ...` / `@alpha ...` / `@delta ...`: 지정된 팀장만 답한다
- `/debate`: Zero의 새 질문 없이 직전에 답한 두 팀장이 서로의 의견에 반박 1회
- 두 팀장이 함께 답할 때는 서로의 답을 보지 않고 독립 작성한다. 그 채널의 최근 대화는 함께 전달한다
- 맥락은 봇이 SQLite 기록으로 매번 재구성해 전달한다 (CLI 세션 이어가기는 최적화 수단)
- 대화에는 상태가 없다. 일로 만들 때 Zero가 `/task`·`/release`로 포럼 포스트를 열고, 봇이 대화의 의견 요약을 옮긴다. 바로 하지 않을 생각은 `/idea`로 남긴다
- 채팅 답의 호출은 팀장별 일일 예산에 들어간다 (SPEC 3.3)

### 1.7 테스트
- 봇이 projects.yaml의 test 명령을 전역 락 아래에서 실행한다
  - 이유: 에이전트의 자기 보고 대신 봇이 직접 확인한 결과를 공식 기록으로 삼는다. 읽기 전용 샌드박스에서는 xcodebuild(DerivedData·시뮬레이터 쓰기)가 실패할 수 있다
- 결과(종료 코드, 통과/실패 수, 실패 테스트명, 소요 시간)를 요약하고 전체 로그는 파일로 저장한다
- 테스트 실패 시 리뷰 담당을 호출하지 않고 바로 구현 담당에게 FIX 요청 (사용량 절약)
- 테스트 실패 재시도 횟수는 리뷰 라운드 제한과 별도로 센다 (2회 초과 시 NEEDS_HUMAN, SPEC Q2)
- 리뷰 담당은 테스트 결과를 입력으로 받아 판정한다: 변경을 검증하는 테스트의 존재, 엣지 케이스 누락, 코드 결함, 기획서 완료 기준 충족

### 1.8 GitHub Issue
- 생성 시점: Zero의 `/task`·`/release` 직후. 채팅에서 끝난 이야기는 Issue를 만들지 않는다 (Discord에만 기록)
- 위치: 각 앱 저장소 (예: GagaeSsi)
- 내용은 봇이 기존 텍스트를 조립한다. 에이전트를 별도로 호출하지 않는다
  - 이유: 결정은 Zero의 원문 그대로 남아야 하고, 추가 호출 비용을 피하며, 작업 정의는 기획 단계에서 이미 작성된다

| 항목 | 출처 |
|---|---|
| 제목 | `/task`의 제목 |
| 결정 | Zero의 `/task` 원문 |
| 배경 | 채팅에서 Zero가 꺼낸 아이디어 원문 |
| 의견 요약 | 채팅 팀장 의견의 stance·conclusion과 risks |
| 링크 | 포럼 포스트, 채팅 메시지 |

- PLANNING·UI_DESIGNING·DESIGNING·DIAGNOSING 완료 시 봇이 요약을 Issue 코멘트로 추가한다
- 브랜치명에 Issue 번호를 포함한다 (예: `feat/42-budget-banner`, 4.2 참고)
- develop merge는 자동 종료(`Closes`)가 동작하지 않으므로, 봇이 merge 감지 시 코멘트를 남기고 Issue를 직접 종료한다 (4.6 참고)
- 예외 처리

| 상황 | 처리 |
|---|---|
| `/task` 후 /stop | 중지 사유를 코멘트로 남기고 "not planned"로 종료 |
| NEEDS_HUMAN | Issue 유지, `needs-human` 라벨 추가 |

### 1.9 GitHub PR
- 내용은 에이전트가 만들고, GitHub에 쓰는 작업은 모두 봇이 한다
- PR 항목별 작성자

| 항목 | 작성자 | 출처 |
|---|---|---|
| 제목 | 봇 | 작업 제목 + 접두어 |
| 결정 | 봇 | Zero의 `/task` 원문 |
| 기획·디자인 요약 | 봇 | 기획·디자인 요약 JSON, Claude 디자인 링크 |
| 변경 요약, 설계 의도, 확인할 점 | 구현 담당 (Epsilon) | 구현 완료 시 요약 블록 |
| 테스트 | 봇 | 봇 실행 결과 |
| 리뷰 이력 | 봇 | 라운드별 판정 요약 |
| Discord 링크, 브랜치, Refs #Issue | 봇 | 작업 정보 |

- 리뷰 본문은 PR 코멘트로 라운드마다 추가한다. 작성자 표시는 `[이름 · 직책]`이다
- PR 본문은 FIX가 끝날 때마다 봇이 갱신한다
- 처음부터 draft로 생성하고, 리뷰 담당(Delta)이 APPROVED를 내면 봇이 draft를 해제한다
- merge는 Zero가 직접 한다

### 1.10 기록의 역할 분담
- Discord 채팅 채널: 결정 전 논의 (의견, 추가 질문, 반박)
- Discord 포럼 포스트: 결정 이후의 진행과 팀 보고
- GitHub Issue: 무엇을 왜 하기로 했는가 (결정)
- GitHub PR: 어떻게 만들었고 어떻게 검증했는가 (구현, 리뷰)
- 앱 저장소 `docs/기획/`, `docs/디자인/`, `docs/설계/`: 기획서, 화면 디자인 명세, 기술 설계 전문
- Obsidian 볼트: 결정 노트, 논의 목록, 기능 정의서 (상세는 3장)
- 조직과 채용 기록: 비공개 회사 저장소의 `org.yaml` (SPEC Q12, Q17)

### 1.11 인터페이스 채널
- 논의와 승인은 Discord에서 한다 (모바일 입력, 푸시 알림, 외부에서 맥으로의 중계, 무제한 기록을 별도 구현 없이 확보). 2026-10-28 Slack과 다시 비교한 뒤 유지했다 (ADR-007)
- 정기 보고(아침·주간)는 `#대표실`에서 받는다 (2.5, SPEC 6.6)
- 여러 프로젝트·파이프라인의 현황과 지표는 로컬 대시보드에서 본다. 대시보드는 SQLite를 읽기 전용으로 읽는다
- 입력은 Discord와 봇 일정뿐이다. 다른 사람이 요청을 넣는 경로는 없다 (ADR-007, SPEC 6.5)
- 봇 토큰은 앱에 넣지 않으며, 개인 계정 토큰 사용(셀프봇)은 하지 않는다

### 1.12 채용

새 팀과 팀원이 필요한 시점은 팀장이 먼저 알아채고 제안한다. 채용 여부와 설정 변경은 Zero가 한다.

- 새 팀 제안: 자기 팀 역량 밖의 일이 반복될 때 (예: 화면 설계 → 디자인팀, 리뷰가 코드 품질에 미치지 못함 → QA팀, 운영 요청이 개발을 밀어냄 → 운영팀)
- 팀원 제안: 의견의 폭이 부족해 다른 관점이 더 필요할 때, 특정 업무를 실제로 맡을 담당이 필요할 때
- 제안 방법: 작업 보고 JSON의 선택 필드 `hiring_proposal`로 붙인다. 제안만 하는 실행은 만들지 않는다 (SPEC Q19)
- 제안 내용: 근거(어떤 작업에서 무엇이 부족했는지), 맡길 업무, 원하는 성격(MBTI)·역량, 채용하지 않을 때의 영향. 대기 시간·실패 수·한도 초과 수 같은 숫자 근거는 봇이 DB에서 계산해 붙인다
- Zero의 답: `/hire`로 수락 또는 거절한다. 수락하면 Zero가 `org.yaml`과 인격 파일을 추가한다. 거절 기록은 다음 프롬프트에 넣어, 새 근거가 생기기 전까지 같은 제안을 반복하지 않게 한다
- 채용 기록(이름, 팀, 직책, 엔진, 성격, 역량, 채용일, 제안한 팀장, 근거)은 `org.yaml`과 ZeroSync 개발 일지에 남긴다

## 2. Discord 대화 형태 (확정)

### 2.1 공통: 에이전트 출력 방식 (확정)
- 에이전트는 미리 정한 JSON 스키마로 출력한다
- 봇은 JSON을 추출해 pydantic 스키마로 검증한 뒤 SQLite에 원본을 저장하고, render 계층에서 Discord 메시지로 변환해 게시한다
- 저장, Discord 표시, Issue·PR·볼트 옮겨 적기는 모두 같은 JSON에서 나온다. 표시 방식 변경은 render 계층만 수정한다
- CLI의 스키마 강제 출력 옵션을 우선 사용하고, 없으면 프롬프트로 JSON 코드 블록을 요청해 추출한다 [검증 필요]
- 검증 실패 시 오류 내용을 붙여 1회 재요청한다. 다시 실패하면 원문을 "형식 오류" 표시와 함께 게시하고 Zero에게 알린다

### 2.2 의견 형식 (확정)
- 필드 4개: 결론 / 근거 / 위험 / 제안 ("질문" 필드는 두지 않음)
- 입장(stance)은 4개 값으로 고정: 찬성 / 조건부 찬성 / 반대 / 대안 제시
- 위험은 찬성이어도 최소 1개 이상 필수 (AI가 찬성 시 단점을 생략하는 경향 방지)

| 필드 | 키 | 제약 |
|---|---|---|
| 입장 | stance | 4개 값 중 하나 |
| 결론 | conclusion | 한 줄, 120자 이내 |
| 근거 | reasons | 1~4개 |
| 위험 | risks | 1~3개 |
| 제안 | proposal | 300자 이내 |

### 2.3 리뷰 판정 형식 (확정)
- 지적은 두 등급으로 구분한다: [필수] / [권장]

| 등급 | 해당하는 경우 |
|---|---|
| [필수] | 버그, 데이터 손실·보안 위험, 기획서·설계와 다른 동작, 기획서 완료 기준 미충족, 변경을 검증하는 테스트 누락, 빌드·테스트를 깨뜨리는 문제 |
| [권장] | 가독성, 이름, 중복 제거, 더 나은 구조, 현재 문제가 없는 성능 개선 |

- 판정 규칙: [필수]가 있으면 CHANGES_REQUESTED, 없으면 APPROVED
- 판정과 지적 등급이 어긋나면 봇이 형식 오류로 처리한다 (스키마 검증으로 강제)
- 필드: verdict, summary(200자), findings 최대 10개 (severity, file, line, problem, reason, suggestion)
- CHANGES_REQUESTED 시 구현 담당(Epsilon)에게 [필수] 항목을 FIX 대상으로 전달한다. [권장]은 참고로 함께 주되 반영 여부는 구현 담당 재량
- APPROVED 후 남은 [권장] 항목은 PR 코멘트로 남기고, 처리 여부는 Zero가 결정한다 (예: merge 전 `/fix 권장 반영`으로 1회 추가 수정)
- APPROVED 시 봇이 Discord에 남은 [권장] 개수를 표시한다
- 리뷰 담당(Delta)은 판정마다 기준 문서에 없는 우려를 최소 1개 적는다. 의견의 위험 필수 규칙(2.2)과 같은 이유다 (ADR-007, 회사 재정의 04-조직 3.2) [제안: 스키마 필드는 Phase 3에서 정함]
- 2라운드부터 리뷰 담당(Delta)은 이전 라운드 [필수] 항목의 해결 여부를 항목별로 확인한다 (등급 하향으로 문제를 놓치는 위험 보완)

### 2.4 기획서·설계 전문 위치 (확정, 3.3 참고)
- Discord에는 기획·디자인·설계 요약과 GitHub 링크(작업 브랜치의 `docs/기획/`, `docs/디자인/`, `docs/설계/` 파일), Claude 디자인 링크만 게시한다

### 2.5 멘션 규칙 (확정)
- 원칙: Zero가 행동해야 할 때만 멘션한다 (알림 피로 방지)

| 상황 | 멘션 | Zero가 할 일 |
|---|---|---|
| 채팅에서 부른 팀장의 답이 모두 도착 | O (채팅 채널) | 추가 질문, `/task`, `/idea` 또는 없음 |
| 기획 완료 | O | /approve 또는 /revise |
| 화면 디자인 완료 | O | Claude 디자인 링크 확인 후 /approve 또는 /revise |
| 진단 완료 (버그 수정) | O | 수정 방향 /approve 또는 /revise |
| 설계 완료 (기획·디자인 승인 뒤, 승인 게이트 없음) | X | 없음 (필요하면 /stop) |
| APPROVED (최종 확인) | O | PR 확인 후 merge |
| 출시 준비 완료 | O | 준비물 확인 후 /approve, 그 뒤 스토어 제출 |
| 문서 반영안 도착 (DOC_SYNC) | O | /approve, /revise, /skip |
| 정기 테스트 실패 보고 | O | `/task bug`로 이어가거나 닫기 |
| NEEDS_HUMAN (리뷰 3회 초과, 테스트 재시도 초과, 형식 오류 반복, 예산 초과) | O | 판단 또는 /stop |
| 아침 보고에 Zero가 할 일이 있음 | O (#대표실) | 승인 대기 처리 |
| 아침 보고에 할 일이 없음, 주간 보고 | X (#대표실) | 없음 |
| 팀장의 채용 제안 (1.12) | O (#대표실) | /hire 수락 또는 거절 |
| 구독 사용량 한도로 대기열 정지 | O (#zerosync-ops) | 없음 (풀리면 다시 시작) 또는 판단 |
| 봇·CLI 오류, 타임아웃, 볼트 쓰기 실패 | O (#zerosync-ops) | 원인 확인 |
| 구현 시작, 테스트 실행 중, 리뷰 진행 중 | X | 없음 |
| 테스트 결과, CHANGES_REQUESTED 라운드 결과 | X | 없음 |

- 구현: 제품 포럼·채팅 채널과 `#대표실` 알림을 "@멘션만"으로 설정. 봇은 행동 필요 이벤트에만 `<@Zero ID>`를 붙이고, 나머지는 무음 메시지(silent)로 보낸다 [검증 필요: 웹훅의 silent 지원]
- 멘션 여부는 이벤트 종류(ACTION_REQUIRED 집합)로 결정하고 단위 테스트로 고정한다
- 방치된 작업: 결정 대기(기획·디자인·수정 방향·출시 승인 대기, 최종 확인 대기, 문서 반영 승인 대기, 정기 테스트 실패 보고, NEEDS_HUMAN, 채용 제안)가 24시간을 넘으면 1회만 다시 멘션한다. 이후에는 아침 보고의 승인 대기 목록과 /status로 확인한다. 채팅의 답은 대기 상태가 아니라 재멘션하지 않는다

### 2.6 길이 규칙 (초안)
- 게시용 요약은 1,500자 이내. 넘는 전문은 파일 첨부
- 1,900자 분할은 예외 상황의 안전장치로만 사용

### 2.7 채널 구성 (확정, 2026-10-28 ADR-007)
- 제품마다 포럼 채널(정식 진행, 팀 보고)과 채팅 채널(의견 나누기): #gagaessi와 #gagaessi-chat, #jday와 #jday-chat, #orot와 #orot-chat (이름은 회사 설정에서 바꿀 수 있다)
- #대표실: 아침·주간 보고, 채용 제안
- #zerosync-ops: 봇 시작·종료, 오류, /ping, 사용량 한도 정지
- 교육·비서 부서의 채팅 채널은 그 부서를 시작할 때 더한다

## 3. 기록 위치 (확정)

### 3.1 원칙
- 정보마다 원본은 한 곳에만 둔다. 다른 곳에는 요약과 링크만 둔다
- 볼트에는 `/task`·`/release`(결정) 이후부터만 기록한다. 결정 전 논의(채팅)는 Discord에만 남는다
- 기능 정의서는 merge(구현 확인) 후에만 생성·갱신한다. 결정만 되고 구현되지 않은 내용은 기능 정의서에 넣지 않는다 (볼트 규칙 "결정되면 결정 노트, 구현 확인 후 기능 갱신"과 일치)

### 3.2 정보별 원본 위치

| 정보 | 원본 | 다른 곳 |
|---|---|---|
| 논의 과정 (의견, 질문, 반박) | Discord 제품 채팅 채널 | 포럼 포스트·Issue·결정 노트에 의견 요약 |
| 결정 (무엇을 왜) | GitHub Issue | 볼트 결정 노트 |
| 기획서 전문 | 앱 저장소 `docs/기획/<Issue번호>-<slug>.md` | Discord·Issue·결정 노트·PR에 요약과 링크 |
| 화면 디자인 명세 | 앱 저장소 `docs/디자인/<Issue번호>-<slug>.md` | Claude 디자인 링크는 명세 안에. Discord·Issue·결정 노트에 요약과 링크 (ADR-007) |
| 제품 디자인 시스템 | Claude 디자인 시스템 (제품마다 1개) | 링크는 비공개 회사 저장소의 제품 설정 (ADR-007) |
| 설계 전문 | 앱 저장소 `docs/설계/<Issue번호>-<slug>.md` | Discord·Issue·결정 노트에 요약과 링크 |
| 진단 보고 | SQLite (에이전트 출력 JSON) | 포럼 포스트·Issue에 요약 (ADR-007) |
| 아이디어 목록 | SQLite | 대시보드. 볼트에는 옮기지 않는다 (ADR-007) |
| 아침·주간 보고 | SQLite에서 매번 만든다 | `#대표실` (ADR-007) |
| 조직과 채용 기록 | 비공개 회사 저장소 `org.yaml` | 채용 제안·답은 SQLite, ZeroSync 개발 일지 |
| 코드, 리뷰, 테스트 결과 | GitHub PR | Discord에 한 줄 결과와 링크 |
| 기능의 현재 동작 | 볼트 기능 정의서 | 허브 기능 지도에 한 줄 |
| 봇 상태, 에이전트 출력 원본 JSON | SQLite | 없음 (로컬 대시보드가 읽음) |
| 테스트·CLI 전체 로그 | 맥 로컬 `.zerosync/runs/` | 커밋하지 않음 |

- ZeroSync 저장소의 `docs/개발 일지/`는 봇 자체 개발 기록이며 위 기록과 분리한다

### 3.3 기획서·디자인 명세·설계 전문 (앱 저장소)
- 위치: 각 앱 저장소의 `docs/기획/<Issue번호>-<slug>.md`(기획 담당 작성), `docs/디자인/<Issue번호>-<slug>.md`(디자인 담당 작성), `docs/설계/<Issue번호>-<slug>.md`(설계 담당 작성) (예: `docs/설계/42-budget-banner.md`). Xcode 타깃 밖이므로 앱 번들에 포함되지 않는다
- 작업 브랜치는 파이프라인의 첫 단계(기능 개발은 PLANNING, 버그 수정은 진단 승인 뒤 IMPLEMENTING)에서 생성한다 (IMPLEMENT가 아니라). 생성 순서는 4.3 참고
- 수정 요청(`/revise`) 시 해당 문서의 담당이 같은 파일을 고쳐 커밋한다. 변경 이력은 git으로 추적한다
- 승인 전 반려(/stop) 시 봇이 작업 브랜치를 삭제한다
- 확인 방법: 작성 직후는 Discord의 GitHub 링크(작업 브랜치 blob), 구현 후는 PR Files changed, merge 후는 develop의 `docs/기획/`, `docs/디자인/`, `docs/설계/`
- 봇은 평소 작업 폴더가 아닌 전용 worktree(예: `~/.zerosync/worktrees/<project>-<issue>/`)에서 작업한다. 경로는 projects.yaml에서 정한다

### 3.7 결정 노트
- 파일: `결정/<프로젝트> - <작업 제목>.md`
- frontmatter

| 키 | 값 |
|---|---|
| type | "decision" |
| status | 결정 → 코드확인(merge 후, 출시 완료를 뜻하지 않음) / 중단 |
| tags | ["project-brain", "node/decision", "brain/<프로젝트>"] |
| project | 프로젝트명 |
| source_id | `zerosync-<project>-<Issue번호>` (중복 방지·갱신 키) |
| zerosync_status | decided / plan_approved / ui_approved / fix_approved / implementing / reviewing / merged / released / doc_synced / stopped (`design_approved`는 ADR-005 기준 값으로 읽기만 한다) |
| change_type | 기능 추가 / 기능 변경 / 버그 수정 / 내부 개선 |
| issue, pr | 번호 |

- 본문 섹션: 선택한 안(Zero 원문) / 이유와 의견(팀장별 stance·conclusion) / 위험과 대안(risks) / 기획 또는 진단(요약 + 링크) / 디자인(요약 + 명세·Claude 디자인 링크) / 설계(요약 + 링크) / 결과(리뷰 라운드, 남은 [권장], merge일) / 출처(Discord, Issue, PR, 기획·설계 문서)
- 링크: 허브, 대상 기능 노트

### 3.8 변경 유형
- `change_type`과 `target_feature`는 파이프라인의 첫 단계 담당이 JSON으로 제안하고(기능 개발은 Beta의 기획 JSON, 버그 수정은 Zeta의 진단 JSON), 그 단계의 `/approve`로 함께 승인된다 (SPEC 5.4)
- 봇은 enum 값과 `target_feature`가 실제 `기능/` 폴더의 파일명인지 검증한다. 제안하는 담당에게는 봇이 해당 프로젝트 `기능/` 파일 목록을 전달한다

| change_type | 의미 | DOC_SYNC에서 |
|---|---|---|
| 기능 추가 | 새 기능 | 새 기능 정의서 생성 + 허브 기능 지도에 행 추가 |
| 기능 변경 | 기존 기능 동작 변경 | 기존 기능 정의서 본문 수정 + 확인 이력 + 허브 행 수정(필요 시) |
| 버그 수정 | 의도대로 고침 | 확인 이력 + 필요 시 예외·코드 근거 수정 |
| 내부 개선 | 동작 동일 | 확인 이력 + 필요 시 코드 근거 수정 |

### 3.9 DOC_SYNC (merge 후 문서 반영)
1. 봇이 진행 중인 PR 상태를 주기적으로 조회해 merge를 감지한다 (예: 5분 간격. 맥은 외부 접속 불가이므로 webhook 대신 조회)
2. 봇이 문서 반영 담당(기능 개발은 Beta)을 읽기 전용으로 호출한다. 입력: merge된 develop 코드, 대상 기능 노트·허브 원문, 결정 노트, 볼트 기능 노트 형식
3. 문서 반영 담당은 수정안 JSON을 출력한다: 파일별 {path, action(create/update), content(전체 내용)}
   - 기능 노트 형식(이 기능이 하는 일 / 현재 처리 흐름 / 예외와 지켜야 할 조건 / 개선 가설과 확인 조건 / 연결 기술 / 코드와 기획 근거 / 확인 이력)을 유지한다
   - 확인 이력에 한 줄 추가: 날짜, PR, 봇 테스트 결과. 실기기·배포는 확인 범위가 아님을 명시
   - status는 "코드확인". 출시 완료로 표기하지 않는다
   - 결정 노트로 가는 링크를 포함한다
4. 봇 검증: 경로가 쓰기 허용 범위인지, frontmatter 필수 키 유지, 대상 파일 존재 여부(update는 존재, create는 미존재)
5. 봇이 Discord에 요약 + diff 파일을 첨부하고 Zero를 멘션한다
6. Zero 명령
   - `/approve`: 봇이 파일을 쓰고 볼트 git에 커밋한다
   - `/revise <요청>`: 문서 반영 담당이 수정안을 다시 작성한다
   - `/skip`: 기능 정의서·허브는 그대로 두고 결정 노트만 완료 처리한다
7. 승인 시점에 대상 파일의 해시가 수정안 생성 시점과 다르면(Zero가 그사이 직접 편집) 쓰지 않고 수정안을 다시 만든다
8. 완료 후 결정 노트 zerosync_status=doc_synced, 논의 목록 상태 "완료"

### 3.10 볼트 git (Obsidian 볼트 저장소 전용. 앱 저장소 커밋은 4.4)
- 볼트는 여러 프로젝트가 한 저장소에 있으므로 scope에 프로젝트 슬러그를 쓴다 (gagaessi, focus, jday)
- 볼트 규칙의 `git add -A` 대신, 봇은 자기가 쓴 파일만 `git add <경로>`로 지정해 항목별로 커밋한다 (Zero가 편집 중인 노트가 섞이지 않게)
- 볼트 규칙 문서에 "ZeroSync 봇은 자기 파일만 커밋" 예외를 추가한다 (Zero가 직접 또는 별도 요청으로)
- 커밋 메시지: 제목 `docs(<프로젝트 슬러그>): ZeroSync <결정|기획 승인|디자인 승인|수정 방향 승인|기능|중단> - <제목>`, 본문 "확인: … / 아직 아님: …", 꼬리말 `ZeroSync-Task: <project>-<Issue번호>`, `Refs: <Issue 또는 PR URL>`
- 커밋 경로 지정: `git add -- <경로>` 후 `git commit -- <경로>` (다른 스테이징 파일이 섞이지 않게)
- 볼트 규칙 예외 문구(봇은 자기 파일만 커밋)는 저장소 연결 후 에이전트가 수정안을 만들고 Zero가 승인한다
- iCloud 동기화 중 쓰기 실패 시 짧게 재시도하고, 계속 실패하면 #zerosync-ops에 알린다 [검증 필요]
- 볼트 루트가 git 저장소인지, 봇 실행 계정에서 접근 가능한지 [검증 필요]

## 4. GitHub 규칙 (앱 저장소, 확정)

### 4.1 브랜치 전략 (Git Flow)
- `main`: 배포 버전 기준. 봇은 main을 읽지도 쓰지도 않는다. develop → main 릴리스는 Zero가 직접 한다
- `develop`: 기능 개발 후 확인·테스트 브랜치. 모든 작업 브랜치의 생성 기준이자 PR 대상
- 작업 브랜치: 기능마다 새로 만든다. 모든 프로젝트(가게씨, 오롯, 제이데이) 공통
- ZeroSync 저장소(봇 자체 개발)도 develop 기준으로 작업 브랜치를 만들고, 스레드당 develop 대상 draft PR을 연다. develop → main 릴리스는 Zero가 직접 한다. 세부 규칙은 저장소의 AGENTS.md를 따르며 이 장의 나머지 항목(봇 자동화)과는 별개다 (2026-10-05 변경, 이전: main 기준)

### 4.2 브랜치 이름
- 형식: `<type>/<Issue번호>-<slug>` (예: `feat/42-budget-banner`). `claude/` 접두어는 쓰지 않는다
- type은 승인된 변경 유형(3.8)으로 결정한다

| 변경 유형 | type |
|---|---|
| 기능 추가, 기능 변경 | feat |
| 버그 수정 | fix |
| 내부 개선 | refactor |

- slug는 첫 단계 담당이 JSON에 제안하고(기능 개발은 기획 JSON, 버그 수정은 진단 JSON) 봇이 형식만 검증한다: `^[a-z0-9]+(-[a-z0-9]+){0,4}$`, 40자 이내

### 4.3 브랜치 생성 순서
1. 봇이 develop 최신 커밋에서 worktree를 만든다 (브랜치 이름 없이 detached 상태)
2. 첫 문서 단계 담당이 문서를 작성·커밋하고 JSON(change_type, slug 포함)을 출력한다. 기능 개발은 Beta가 `docs/기획/<Issue번호>-<slug>.md`를 쓴다
3. 봇이 JSON을 검증하고 브랜치 이름을 정해 현재 커밋에 브랜치를 만든 뒤 push한다
4. 승인 전 수정(`/revise`)으로 변경 유형이 바뀌면 봇이 새 이름으로 push하고 이전 원격 브랜치를 삭제한다 (PR 생성 전이므로 영향 없음)
5. 버그 수정은 진단이 읽기 전용이라 문서를 커밋하지 않는다. 수정 방향 승인 뒤 봇이 진단 JSON의 slug로 브랜치를 만들고 구현을 시작한다 (ADR-007)

### 4.4 앱 저장소 커밋 메시지
- 형식: `<type>(<영역>): <요약>` + 빈 줄 + 본문(선택) + 꼬리말 `Refs: #<Issue번호>`
- 단일 프로젝트 저장소이므로 scope에 프로젝트명을 쓰지 않는다. scope는 앱 내부 영역(budget, spend, settings 등)이며 애매하면 생략한다
- type: feat / fix / refactor / test / docs / chore
- merge commit 방식이므로 모든 커밋이 develop 이력에 남는다. 커밋 단위 예시

| 커밋 | 예시 |
|---|---|
| 기획서 | `docs(plan): 예산 초과 배너 기획` |
| 화면 디자인 명세 | `docs(ui): 예산 초과 배너 화면 디자인` |
| 설계 문서 | `docs(design): 예산 초과 배너 설계` |
| 구현 (논리 단위) | `feat(budget): 월 지출 합계 캐시 추가` |
| 테스트 | `test(budget): 월 경계 시간대 테스트 추가` |
| 리뷰 반영 | `fix(budget): 리뷰 1라운드 [필수] 1·2 반영` |

- `wip`, `수정` 같은 의미 없는 메시지 금지
- 봇은 push 전에 커밋 메시지 형식을 정규식으로 검사하고, 틀리면 push 전에 커밋한 담당 에이전트에게 수정을 요청한다 (push 전이므로 이력 수정 허용)
- push 후에는 force push 금지. 리뷰 반영은 항상 새 커밋으로 추가한다

### 4.5 PR
- 대상: develop. 처음부터 draft로 생성하고 리뷰 담당의 APPROVED 시 draft 해제 (1.9 참고)
- 제목: `<type>(<영역>): <요약>` (예: `feat(budget): 월 예산 초과 시 홈 화면 배너 표시`)
- 본문 꼬리에 `Refs #<Issue번호>` (develop merge에서는 Closes가 동작하지 않으므로 사용하지 않음)

### 4.6 merge와 정리
- merge 방식: Merge commit (작업 브랜치의 모든 커밋이 develop에 보이고, merge 커밋이 기능 단위 경계를 남김. 되돌릴 때 `git revert -m 1 <merge커밋>`)
- merge는 Zero가 GitHub에서 직접 한다
- 봇이 PR 상태 조회로 merge를 감지하면: Issue에 "develop merge 완료" 코멘트 후 Issue 종료 → DOC_SYNC 시작
- 저장소 설정 "Automatically delete head branches"를 켜서 원격 작업 브랜치를 자동 삭제한다
- 맥의 worktree는 DOC_SYNC 완료 후 봇이 정리한다

### 4.7 봇의 push 보호
- 두 조건을 모두 만족할 때만 push한다
  1. 브랜치 이름이 `^(feat|fix|refactor)/\d+-[a-z0-9]+(-[a-z0-9]+)*$` 형식 (main, develop은 형식에서 제외됨)
  2. 해당 작업에서 봇이 만든 브랜치로 SQLite에 기록된 이름과 일치 (Zero가 직접 만든 같은 형식의 브랜치는 건드리지 않음)
- GitHub 브랜치 보호(rulesets)로 main·develop 직접 push 금지를 함께 건다 [검증 필요: 개인 private 저장소 요금제에서 사용 가능 여부]

### 4.8 라벨
| 라벨 | 대상 | 시점 |
|---|---|---|
| `zerosync` | Issue, PR | 생성 시 |
| `type:feature` / `type:fix` / `type:refactor` | Issue, PR | 변경 유형 승인 시 (기획 승인, 버그 수정은 수정 방향 승인) |
| `needs-human` | Issue, PR | NEEDS_HUMAN 진입 시, 해결되면 제거 |

- 봇이 처음 실행될 때 저장소에 라벨이 없으면 만든다
