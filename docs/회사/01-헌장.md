# 01. 회사 헌장

> 상태: 확정 (2026-10-27)
> 회사 재정의 1단계. 회사가 무엇을 위해 무엇을 하는지 정한다. 2단계(프로젝트 목록)부터 6단계(시스템 반영)까지는 이 문서를 판단 기준으로 쓴다.

---

## 1. 왜 다시 정하나

| 시점 | 무엇을 만들려 했나 | 근거 |
|------|------------------|------|
| v1 | macOS 메뉴바 AI 비서 앱 | ADR-001~004 (보류) |
| v2 초기 | 프로젝트 하나의 기능 개발을 Discord로 원격 진행하는 봇 | ADR-005 |
| 2026-10-26 | 기획팀·개발팀 팀장과 채용 구조, 파이프라인 선언, 여러 입력 경로 | ADR-006 |
| 지금 | 여러 부서가 Zero의 성장, 일상 정보, 제품을 나눠 맡는 회사 | 이 문서 |

ADR-006은 조직(사람)부터 정했다. 회사가 할 일이 정해지지 않으면 그 조직이 맞는지 판단할 수 없으므로, 이 문서에서 할 일부터 정한다.

---

## 2. 목적

ZeroSync는 **Zero 한 사람을 위한 회사**다.

> Zero의 제품, 본업, 성장, 일상 정보를 팀이 나눠 맡아, Zero는 판단에만 시간을 쓴다.

Zero가 대표로 방향을 정하고 승인하며, 부서와 팀이 실행하고 보고한다. 회사의 고객은 Zero 한 명이다. 다른 사람이 회사에 요청을 넣는 경로는 두지 않는다.

목적 문장의 "본업"은 제품 부서가 맡는 Zero의 제품을 말한다. 회사 밖 직장의 현장 업무 지원은 회사 범위에 넣지 않는다 (2026-10-27 Zero 결정).

---

## 3. 부서

회사는 **부서 → 팀** 두 층으로 나눈다. 부서는 회사가 하는 일의 분야이고, 팀은 부서 안에서 단계나 기능을 맡는다. 팀 이름, 팀장, 인원은 4단계(조직과 직원)에서 정한다.

| 우선순위 | 부서 | 하는 일 | 입력 | 결과물 |
|---------|------|--------|------|-------|
| 1 | 교육 | Zero의 성장: 학습 계획, 학습 자료, 진도 확인 | Zero의 학습 목표 | 학습 계획, 정리 자료 |
| 2 | 비서 | 새 IT 이슈를 묶어 정기 공유, 개인 메일 정리(보류), Zero가 요청한 지식·정보 조회 후 보고 | 뉴스·기술 소식, Zero의 메일, Zero의 요청 | 정기 브리핑, 정리 요약, 조회 보고, 답장 초안 |
| 3 | 제품 | Zero 제품의 전체 생애: 새 제품(아이디어 → 디자인 → 기획 → 개발 → 출시)과 운영 중인 제품(개선, 유지보수, 장애 대응, 의견 나누기) | Zero의 아이디어, 앱 문제 보고 | 기획서, 코드(PR), 테스트 결과, 출시 준비물 |

- 우선순위는 일이 몰리거나 예산(ADR-006 Q18)이 부족할 때 어느 부서의 일을 먼저 처리할지의 기준이다
- 직장의 현장 업무 지원(직장 앱 빌드·상태 확인, 인증서 관리, 야간 시나리오 테스트, 테스트 베드 요청)은 회사 범위에서 뺀다 (2026-10-27 Zero 결정)
- 개인 메일 정리는 나중에 정한다. 지금은 고려하지 않는다 (2026-10-27 Zero 결정)

### 3.0 보고 구조 (2026-10-27 Zero 결정)

| 부서 | 부서장 | 보고 방식 |
|------|-------|----------|
| 제품 | Zero (대표 겸임) | 팀장마다 Zero에게 직접 보고 |
| 교육 | 없음 | 담당 에이전트와 Zero의 1대1 미팅 |
| 비서 | 없음 | 담당 에이전트와 Zero의 1대1 미팅 |

- 부서장을 따로 두지 않는다. 제품 부서는 ADR-006의 "팀장 직접 보고"를 그대로 따른다
- 교육·비서는 팀장 보고 체계 없이 Zero와 담당 에이전트가 1대1로 만난다. 미팅 주기와 형식은 3단계(업무 흐름)와 5단계(운영 방식)에서 정한다

### 3.1 제품 부서의 팀 (큰 틀)

| 팀 | 맡는 단계 |
|----|----------|
| 기획 | 아이디어 정리, 기획서 (ADR-006의 기획팀, 팀장 Beta) |
| 디자인 | 화면 디자인 (2026-10-27 추가) |
| 개발 | 설계, 구현 (ADR-006의 개발팀, 팀장 Alpha) |
| 검증 | 만든 것이 기획과 맞는지, 코드가 올바른지 확인 |
| 테스트 | 빌드, 자동 테스트, 실패 진단 |
| 배포 | 출시 준비, 인증서 관리, 스토어 제출 (실행은 Zero 승인 후) |

팀이 맡는 일의 경계(검증과 테스트의 구분 등)는 [03-업무-흐름.md](03-업무-흐름.md) 2장에 있다.

---

## 4. 하지 않는 일과 승인이 필요한 일

**하지 않는 일** (Zero가 직접 한다)

- 비용 지출: 유료 서비스 가입, 결제, 구독

**Zero 승인 후에만 하는 일**

- 신규 기획 시작, merge, 배포 (ADR-006)
- 외부로 나가는 모든 것: 메일 답장, 앱 리뷰 답장, 홍보 글·SNS 게시. 팀이 초안을 써서 Zero에게 공유하고, Zero가 승인하면 보낸다. 승인 없이 내보내지 않는다

---

## 5. 성공 기준

1년 뒤(2027-10) 아래 기준으로 회사가 잘 돌아가는지 판단한다. 측정 방법은 초안이며 5단계(운영 방식)에서 대시보드 지표로 확정한다.

| 부서 | 기준 | 측정 방법 (초안) |
|------|------|----------------|
| 교육 | 학습 계획 이행률 | 계획한 학습 항목 중 기간 안에 끝난 비율 |
| 비서 | 꾸준한 관리 | 정기 브리핑을 정한 주기대로 낸 비율 |
| 비서 | 조회 보고 수 | Zero가 요청한 지식·정보를 조회해 보고한 횟수 |
| 제품 | 출시·업데이트 수 | 출시한 제품 수, 운영 제품의 merge·출시 횟수 |
| 제품 | 자동 처리 요청 수 | 들어온 요청 중 Zero가 실행에 손대지 않고 끝난 비율 |
| 제품 | 품질 지표 | merge 후 되돌린 변경 수, 장애 대응 시간, 테스트 통과율 |

---

## 6. Zero의 역할

- 대표이자 제품 부서장. 제품 팀장들의 보고를 직접 받는다
- 교육·비서 담당과 1대1 미팅
- 방향 결정: 새 제품, 부서 우선순위, 조직 변경(채용)
- 승인: 기획, merge, 배포, 외부로 나가는 것
- 비용 지출
- 실행에는 들어가지 않는다. 실행이 막히면 팀이 Zero에게 묻는다

---

## 7. 이 결정이 바꾸는 것

다음 단계와 기존 문서에서 다뤄야 할 영향이다. 여기서 정하지 않는다.

- **회사의 일이 코드만이 아니다.** 지금 SPEC은 모든 작업이 Git 저장소의 변경(브랜치, PR, merge)으로 끝난다고 가정한다. 교육·비서 부서는 결과물이 문서·브리핑·초안이라 다른 흐름이 필요하다 (3단계)
- **조직이 두 층이 된다.** 보고 구조는 3.0에서 정했다(제품 부서장은 Zero, 교육·비서는 1대1). ADR-006의 기획팀·개발팀을 제품 부서 소속으로 옮기는 것과 교육·비서 담당 에이전트의 인원·인격은 4단계에서 정하고 ADR-006을 고친다
- **팀 수가 늘어난다.** 제품 부서만 팀 다섯이다. 처음부터 모두 두지 않고 ADR-006의 채용 방식(팀장 제안 → Zero 채용)으로 늘릴지 4단계에서 정한다
- **입력 경로.** SPEC Q14의 Slack·Jenkins·테스트 베드 SSH 입력은 직장 업무 지원을 위한 것이었다. 직장 업무를 뺐으므로 입력 경로를 다시 정하고 6단계에서 SPEC에 반영한다 (02-프로젝트 4장)
- **민감한 입력.** 개인 메일 정리(보류)를 시작할 때 공개 저장소에 들어가지 않게 하는 범위와 에이전트 접근 권한(읽기 전용 여부, 메일 발송 권한)을 함께 정한다. ADR-006의 공개 범위(엔진 공개, 회사 설정 비공개)를 넓혀야 할 수 있다
- **SPEC 1.2(범위 밖)와 v1.** SPEC 1.2는 "v1의 일정·번아웃 관리 기능"과 "릴리스"를 범위 밖으로 둔다. 비서 부서는 v1 메뉴바 비서 앱과 겹치는 부분이 있고, 배포팀의 출시는 릴리스와 겹친다. 6단계에서 범위를 다시 쓴다
