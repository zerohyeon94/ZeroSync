# 01. 회사 헌장

> 상태: 초안 (2026-10-27)
> 회사 재정의 1단계. 회사가 무엇을 위해 무엇을 하는지 정한다. 2단계(프로젝트 목록)부터 6단계(시스템 반영)까지는 이 문서를 판단 기준으로 쓴다.
> `[미결]`은 Zero가 아직 정하지 않은 항목이다.

---

## 1. 왜 다시 정하나

| 시점 | 무엇을 만들려 했나 | 근거 |
|------|------------------|------|
| v1 | macOS 메뉴바 AI 비서 앱 | ADR-001~004 (보류) |
| v2 초기 | 프로젝트 하나의 기능 개발을 Discord로 원격 진행하는 봇 | ADR-005 |
| 2026-10-26 | 기획팀·개발팀 팀장과 채용 구조, 파이프라인 선언, 여러 입력 경로 | ADR-006 |
| 지금 | 여러 팀이 Zero의 제품, 본업, 성장, 일상 업무를 나눠 맡는 회사 | 이 문서 |

ADR-006은 조직(사람)부터 정했다. 회사가 할 일이 정해지지 않으면 그 조직이 맞는지 판단할 수 없으므로, 이 문서에서 할 일부터 정한다.

---

## 2. 목적

ZeroSync는 **Zero 한 사람을 위한 회사**다. Zero가 대표로 방향을 정하고 승인하며, 팀이 실행하고 보고한다.

`[미결]` 한 문장 정의. 초안: "Zero의 제품, 본업, 성장, 일상 정보를 팀이 나눠 맡아, Zero는 판단에만 시간을 쓴다."

---

## 3. 사업 영역

Zero가 말한 회사의 일을 네 영역으로 나눈다. 영역은 "회사가 하는 일"의 구분이며, 영역마다 팀을 따로 둘지는 4단계(조직과 직원)에서 정한다.

| 영역 | 하는 일 | 입력 | 결과물 |
|------|--------|------|-------|
| 제품 | 새 제품: 아이디어 → 디자인 → 기획 → 개발 → 출시. 운영 중인 제품: 개선, 유지보수, 장애 대응, 의견 나누기 | Zero의 아이디어, 앱 문제 보고 | 기획서, 코드(PR), 출시 준비물 |
| 본업 지원 | 본업 회사의 요청 처리: 업무 접수, 빌드·상태 확인, iOS 인증서 관리, 야간 시나리오 테스트, 테스트 베드 요청 | Slack 봇, 로컬 Jenkins, 테스트 베드 SSH | 처리 결과, 보고 |
| 교육 | Zero의 성장: 학습 계획, 학습 자료, 진도 확인 | Zero의 학습 목표 | 학습 계획, 정리 자료 |
| 비서 | 새 IT 이슈를 묶어 공유, 개인 메일 등 정리 | 뉴스·기술 소식, Zero의 메일 | 정기 브리핑, 정리 요약 |

`[미결]` 영역 사이의 우선순위. 동시에 할 일이 몰렸을 때와 예산이 부족할 때 어느 영역을 먼저 처리할지.

---

## 4. 하지 않는 일과 승인이 필요한 일

**하지 않는 일** (Zero가 직접 한다)

- 비용 지출: 유료 서비스 가입, 결제, 구독

**Zero 승인 후에만 하는 일** (ADR-006에서 정한 것)

- 신규 기획 시작, merge, 배포

`[미결]` 외부로 나가는 일의 승인 규칙. 이번 결정에서 "하지 않는 일"로 고르지 않은 항목이다. 회사가 하되 승인을 받을지, 승인 없이 할지 정해야 한다.

| 항목 | 예 |
|------|----|
| 외부 사람에게 보내기 | 메일 답장, 본업 Slack 답글, 앱 리뷰 답장 |
| 배포·스토어 제출 | App Store 제출, 운영 서버 반영 (ADR-006상 승인 필요) |
| 마케팅·홍보 | 홍보 글, SNS 게시 |

---

## 5. 성공 기준

1년 뒤(2027-10) 아래 기준으로 회사가 잘 돌아가는지 판단한다. 측정 방법은 초안이며 5단계(운영 방식)에서 대시보드 지표로 확정한다.

| 기준 | 측정 방법 (초안) |
|------|----------------|
| 출시·업데이트 수 | 출시한 제품 수, 운영 제품의 merge·출시 횟수 |
| 자동 처리 요청 수 | 들어온 요청 중 Zero가 실행에 손대지 않고 끝난 비율 |
| 품질 지표 | merge 후 되돌린 변경 수, 장애 대응 시간, 테스트 통과율 |

`[미결]` 교육·비서 영역의 기준. 위 세 기준은 제품·본업 지원 영역만 잰다. 예: 학습 계획 이행률, 브리핑을 읽고 실제로 쓴 비율.

---

## 6. Zero의 역할

- 방향 결정: 새 제품, 영역 우선순위, 조직 변경(채용)
- 승인: 기획, merge, 배포, 4장에서 승인으로 정한 일
- 비용 지출
- 실행에는 들어가지 않는다. 실행이 막히면 팀이 Zero에게 묻는다

---

## 7. 이 결정이 바꾸는 것

다음 단계와 기존 문서에서 다뤄야 할 영향이다. 여기서 정하지 않는다.

- **회사의 일이 코드만이 아니다.** 지금 SPEC은 모든 작업이 Git 저장소의 변경(브랜치, PR, merge)으로 끝난다고 가정한다. 교육·비서 영역은 결과물이 문서나 브리핑이라 다른 흐름이 필요하다 (3단계).
- **조직 구분 기준.** ADR-006은 기능별 팀(기획팀, 개발팀)이다. 이번 영역은 업무 분야별(제품, 교육, 비서)이다. 둘을 어떻게 맞출지 4단계에서 정한다.
- **민감한 입력.** 개인 메일과 본업 회사 정보가 들어온다. 공개 저장소에 들어가지 않게 하는 범위와 에이전트 접근 권한(읽기 전용 여부)을 5단계에서 정한다. ADR-006의 공개 범위(엔진 공개, 회사 설정 비공개)를 넓혀야 할 수 있다.
- **SPEC 1.2(범위 밖)와 v1.** SPEC 1.2는 "v1의 일정·번아웃 관리 기능"과 "릴리스"를 범위 밖으로 둔다. 비서 영역은 v1 메뉴바 비서 앱과 겹치는 부분이 있고, 제품 영역의 출시는 릴리스와 겹친다. 6단계에서 범위를 다시 쓴다.
