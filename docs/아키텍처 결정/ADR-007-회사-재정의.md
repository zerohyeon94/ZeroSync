# ADR-007 — 회사 재정의: 부서 구조와 제품 부서 운영

> 날짜: 2026-10-28 | 상태: 확정 (2026-10-28) | 이전 결정: [ADR-006](ADR-006-회사형-구조.md) (일부 대체) | 근거 문서: [회사 재정의 1~5단계](../회사/README.md)

---

## 결정

ZeroSync를 **Zero 한 사람을 위한 회사**로 다시 정의한다. 회사는 부서 → 팀 두 층으로 나누고, 이번에는 제품 부서의 일, 조직, 운영 방식을 정한다. 교육·비서 부서는 제품 부서를 완성한 뒤 같은 순서로 정한다.

> 목적: Zero의 제품, 본업, 성장, 일상 정보를 팀이 나눠 맡아, Zero는 판단에만 시간을 쓴다.

ADR-005의 원칙(봇은 결정론적 프로그램, 판단은 Zero만, 외부 쓰기는 봇 하나, 워크플로 로직은 Discord와 분리)과 ADR-006의 원칙(조직은 Zero만 바꾼다, 팀장이 채용을 먼저 제안한다, 엔진은 설정, 만든 쪽과 검증하는 쪽은 다르다)은 유지한다.

### 1. 부서와 범위 ([01-헌장](../회사/01-헌장.md))

| 우선순위 | 부서 | 하는 일 | 보고 |
|---|---|---|---|
| 1 | 교육 | Zero의 학습 계획, 자료, 진도 (Obsidian 볼트 기반) | 담당 에이전트와 Zero 1대1 |
| 2 | 비서 | IT 이슈 확인(특별한 사건이 있는 날만 보고), 지식·정보 조회 보고. 메일 정리는 보류 | 담당 에이전트와 Zero 1대1 |
| 3 | 제품 | 가게씨, 제이데이, 오롯의 기획부터 출시·운영까지 | 팀장이 Zero(제품 부서장 겸임)에게 직접 |

- 회사의 고객은 Zero 한 명이다. 다른 사람이 요청을 넣는 경로는 없다
- 직장의 현장 업무 지원(직장 앱 빌드·인증서·야간 테스트·테스트 베드, 직장 Slack)은 회사 범위에서 뺀다
- 하지 않는 일: 비용 지출. 승인 후에만 하는 일: 신규 기획, merge, 배포, 외부로 나가는 모든 글(초안 → Zero 승인 → 발송)

### 2. 제품 목록 ([02-프로젝트](../회사/02-프로젝트.md))

| 우선순위 | 제품 | 상태 | 지금 목표 |
|---|---|---|---|
| 1 | 가게씨 | 개발 | 빠르게 안정화해서 첫 출시 |
| 2 | 제이데이 | 운영 | 필요한 기능 업데이트 |
| 3 | 오롯 | 개발 | 개선 방안 논의, 아이디어 관리 |

일의 단위는 프로젝트, 정기 업무, 요청 셋이다. 제품의 생애 주기는 아이디어 → 기획 → 개발 → 출시 → 운영 → 종료(어디서든 보류)다.

### 3. 입력과 채널

- 입력은 **Discord와 봇 일정** 두 가지다. Slack 어댑터, Jenkins 연동, 테스트 베드 SSH는 만들지 않는다. 나중에 경로가 필요하면 같은 대기열에 넣는 로컬 접수 명령만 더한다
- Slack과 다시 비교한 뒤 Discord를 유지한다 (이미 구현·확인, 포럼이 작업판에 맞음, 기록 보존 제한 없음)
- 제품마다 **포럼(정식 진행과 팀 보고)과 채팅(의견 나누기)** 한 쌍을 둔다. 교육·비서는 채팅 채널 하나씩, 정기 보고는 `#대표실`, 봇 상태·오류는 `#zerosync-ops`

### 4. 업무 흐름 ([03-업무-흐름](../회사/03-업무-흐름.md))

| 흐름 | 시작 | 단계와 승인 |
|---|---|---|
| 대화 | 채팅 | 부른 팀장이 답. 아무도 안 부르면 기획팀장·개발팀장 모두 |
| 기능 개발 | `/task feature` | 기획 → [승인] → 화면 디자인(화면 변경 있을 때) → [승인] → 기술 설계 → 구현 → 테스트 → 검증 → [merge] → 문서 반영 → [승인] |
| 버그 수정 | `/task bug` | 진단 → [수정 방향 승인] → 수정 → 테스트 → 검증 → [merge] |
| 출시 | `/release` | 출시 점검 → 출시 준비 → [승인] → Zero가 직접 스토어 제출 |
| 정기 테스트 | 봇 일정 | 실패 때만 진단 후 보고. 수정은 Zero가 `/task bug`로 시작 |
| 아이디어 관리 | `/idea` | 봇 DB의 목록에 기록 |

- 의견 단계는 포럼에서 채팅으로 옮긴다. `/task`가 지금의 `/decide`를 대신한다
- 화면 디자인은 Claude 디자인(제품마다 디자인 시스템, 기능마다 디자인 링크)과 개발팀용 명세(md)를 함께 쓴다. 비대화형 실행에서 만들 수 없으면 명세만으로 시작한다
- 흐름을 만드는 순서: 대화 → 기능 개발 → 버그 수정 → 출시 → 정기 테스트 → 아이디어 관리

### 5. 조직 ([04-조직](../회사/04-조직.md))

```
Zero (대표, 제품 부서장)
└─ 제품 부서
   ├─ 기획팀   Beta  (INFJ)  배포 업무 겸임
   ├─ 디자인팀 Gamma (ISFP)  2026-10-28 채용
   ├─ 개발팀   Alpha (INTJ)
   └─ QA팀     Delta (ISTJ)  검증과 테스트 진단. 2026-10-28 채용
```

- 리뷰(검증)는 처음부터 Delta가 맡는다. Beta는 리뷰하지 않는다
- 다음 채용 이름은 Epsilon이다. 배포 겸임은 출시가 쌓이면 Beta가 채용을 제안한다

### 6. 운영 ([05-운영](../회사/05-운영.md))

- 보고: 단계 보고는 포럼 포스트, 아침 보고(매일 08:00)와 주간 보고(월요일 08:00)는 `#대표실`. 아침·주간 보고는 봇이 DB에서 만든다
- 에이전트는 한 번에 하나만 실행한다. 대기열 순서는 Zero가 방금 답한 일과 채팅 → 제품 우선순위 → 버그·출시·기능 → 접수 순
- 예산 시작값: 팀장마다 하루 30회, 기능 개발 25회·4시간, 버그 12회·2시간, 출시 8회·1시간, 정기 테스트 진단 3회·30분. 2주 뒤 조정
- 구독 사용량 한도에 걸리면 대기열을 멈추고 한도가 풀리면 다시 시작한다
- 대시보드: 홈(승인 대기), 제품별 작업판, 지표, 병목, 아이디어, 예산

Phase 2는 실제 사이클을 한 번 돌린 뒤 PR을 연다. 이후는 운영화를 먼저 한다 (Zero 결정).

## 맥락

- ADR-006(2026-10-26)은 사람(팀장, 채용)부터 정했다. 하루 뒤 Zero가 목표를 "프로젝트 하나 원격 관리"에서 "여러 일을 맡는 회사"로 넓히면서, 회사가 할 일이 정해지지 않아 조직이 맞는지 판단할 기준이 없었다
- 그래서 목적 → 일 → 사람 → 운영 방식 → 시스템 순서로 다시 정했다 (2026-10-27~28, `docs/회사/` 1~5단계)

## 근거

- 할 일부터 정하자 조직의 빈자리가 드러났다: R1(리뷰 담당 ≠ 기획 담당)과 SPEC 예시(Beta가 기획·리뷰)의 충돌, 코드 품질 리뷰의 약점, 화면 디자인 담당 부재. QA팀과 디자인팀으로 메웠다
- 직장 업무를 빼면서 입력 계층의 대부분(Slack 어댑터, Jenkins, SSH)이 필요 없어졌다. 구현 범위가 줄고 공개 저장소에 두기 어려운 어댑터도 사라진다
- 채팅과 포럼을 나누면 가벼운 논의는 메신저처럼 하고, 정식 진행은 작업판으로 볼 수 있다
- 동시 실행 하나와 예산 시작값은 구독 사용량 한도 안에서 안전하게 시작하기 위한 것이다. 병목은 대시보드에서 보고 늘린다

## 트레이드오프

- **호출 증가:** 팀장이 넷이 되고 화면 디자인 단계가 생겨 기능 하나의 호출이 늘었다(최대 약 15회). 동시 실행 하나와 겹쳐 처리 속도가 느려질 수 있다
- **채팅 비용:** 채팅의 말 한마디마다 에이전트 호출이 생긴다. 아무도 부르지 않으면 두 팀장이 모두 답하므로 호출이 두 배다. 팀장별 일일 예산에 포함해 막는다
- **Claude 디자인 의존:** 공개 API가 없고 비대화형 실행 가능 여부가 확인되지 않았다. 안 되면 Zero가 화면을 눈으로 보지 못한 채 승인한다
- **가게씨 출시 지연:** 운영화를 먼저 하므로 가게씨 버그 수정·출시 흐름은 Phase 6이다. 그 전에는 Phase 2 기능 개발 흐름과 수동 작업으로 안정화한다
- **문서·코드 변경 범위:** SPEC, 운영 규약, 프롬프트, 상태 머신, Discord 입력 판정(포럼만 → 포럼 + 채팅)을 바꿔야 한다

## ADR-006에서 대체하는 부분

| ADR-006 | 이 ADR |
|---|---|
| 결정 첫머리: 회사가 하는 일 두 가지(운영, 신규) | 1절의 세 부서와 범위 |
| 1절: 팀장이 직접 보고하는 한 층 조직 | 부서 → 팀. 제품 팀장 보고는 같음 |
| 5절: QA 채용 전까지 Beta가 리뷰 | 처음부터 Delta가 리뷰 |
| 7절: Slack·Jenkins·SSH 입력 | Discord + 봇 일정 |
| 8절: 회사 업무용 어댑터는 비공개 | 어댑터를 만들지 않음. 회사 설정만 비공개 |

ADR-006의 2절(Beta·Alpha 역량과 성격), 3절(채용 방식), 4절(엔진), 5절의 나머지(새 세션 읽기 전용 리뷰, 봇이 테스트 실행), 6절(자율성)은 그대로다.
